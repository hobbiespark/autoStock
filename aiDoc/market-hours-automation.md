# 장중 할 일 자동 실행 (2026-10-06)

- 날짜: 2026-10-06(화) 밤, 장외 구현
- 요청: 사용자 22:19 "장중에 해야 하는일 스케줄 로 자동 실행 가능 토록"
- 근거: 10/6 로그 점검 6절 "장중에만 할 수 있는 남은 일"(`upgrade-2026-10/14-log-review-2026-10-06.md`)
- 적용: 다음 재기동부터. 1.6 실측은 **10/7 10:00**에 한 번 돈다(그 전에 재기동해야 한다).

## 1. 목적과 결정

장중에 사람이 화면을 봐야 했던 일을 앱 안의 스케줄 작업으로 옮긴다. 앱은 장중 내내 떠 있으므로 앱이 하는 것이 가장 확실하다.

| 할 일 | 자동화 | 시각 | 결과가 남는 곳 |
|---|---|---|---|
| C3 09:05 판단 확인 | 판단 요약을 텔레그램으로 한 줄, 09:15에 실행 기록 확인 | 매 거래일 | 텔레그램, 로그 |
| 장중 헬스 확인 | 상태 한 줄 — 이상이 있을 때만 텔레그램 | 매 거래일 10:00·14:00 | 로그 `장중 점검 10:00 — …` |
| 1.6 TR 실측 | 지정가 1주 매수 → 조회 → 취소 → 조회 | 10/7 10:00 한 번 | `docs/measured/tr_probe_20261007_*.json`, 텔레그램 |
| 잔고↔장부 대사 | 자동화하지 않음 — 켜기는 사용자 결정(설정 한 줄) | — | — |
| 외부 heartbeat | 자동화할 수 없음 — Healthchecks URL이 있어야 한다 | — | — |

## 2. 동작

### 2.1 전략 실행 알림과 09:15 확인 — `monitor.MarketDayCheck`

- C3가 09:05 정기 실행(국면 판정까지 간 실행)을 마치면 새 이벤트 `StrategyRunCompleted`를 낸다. 내용은 실행 로그와 같은 한 줄이다.
- `MarketDayCheck`가 그 한 줄을 텔레그램 INFO로 보낸다. 종목 판단 오류가 있으면 WARN이다.
  - 예: `C3 판단 2026-10-07 — 국면 ON(…) · 매수 0 · 매도 0 · 보유 유지 0 · 미진입 0 · 주기 전 5 · 데이터 부족 0 · 오류 0 · 다음 판단 2026-11-05부터`
- 09:15에 오늘 실행 기록이 없으면 WARN을 보낸다. 거래일이고 C3가 켜져 있을 때만 본다.
  - 매매 시스템이 RUNNING이면 `C3 오늘(…) 09:05 실행 기록 없음 — 로그의 C3 줄 확인 필요`
  - 아니면 `C3 오늘(…) 실행 안 함 — 매매 시스템 상태 STOPPED` 등

### 2.2 장중 상태 점검 — 10:00·14:00

- 거래일이고 세션이 ACTIVE일 때만 돈다.
- actuator와 같은 헬스 인디케이터(`kiwoomWs`·`kiwoomAuth`·`killSwitch`)를 이름으로 읽고, 지표 `orders.unknown.count`·`orders.cancel_requested.count`를 더한다.
- 정상이면 로그 한 줄만 남긴다. 예: `장중 점검 10:00 — WS UP(연결·로그인, 마지막 메시지 4초 전) · 토큰 UP(만료 10/08 07:03) · 킬스위치 꺼짐 · UNKNOWN 0 · 취소 요청 0`
- 이상이면 같은 줄 앞에 이상 목록을 붙여 텔레그램 WARN으로도 보낸다. 이상으로 보는 것:
  - WS가 UP이 아니거나, 연결·로그인이 안 됐거나, 마지막 메시지가 120초보다 오래됐거나, 메시지를 받은 적이 없음
  - 토큰 헬스가 UP이 아님
  - 킬스위치 작동 중
  - UNKNOWN 주문이 1건 이상

### 2.3 1.6 TR 실측 — `execution.TrProbeJob`

- **언제:** `execution.tr-probe.date`(2026-10-07) 하루, `at`(10:00) 이후 첫 분에 한 번. 14:50 뒤로는 시작하지 않는다(마감 동시호가 전에 끝낸다).
- **순서(TR 호출 22건):**
  1. 현재가 `ka10001`
  2. 매수 `kt10000` — KODEX 200(069500) 1주, 현재가보다 15% 낮은 지정가(호가 단위로 내림). 체결되지 않을 가격이다.
  3. 3초 기다린 뒤 미체결이 살아 있는 상태에서 조회 15건
     - `ka10075` 미체결 5건: 앱이 지금 쓰는 파라미터(`all_stk_tp=1`, `stk_cd` 없음), 스펙의 전체(`all_stk_tp=0`), 종목 지정, 거래소 KRX·NXT
     - `kt00007` 주문체결내역상세 6건: 주문순 전체, 날짜 지정, 미체결만(`qry_tp=3`), 거래소 KRX·NXT·SOR
     - `ka10076` 체결 4건: 종목 지정, 전체, KRX, NXT(미체결이라 빈 목록 모양을 본다)
  4. 취소 `kt10003`(`cncl_qty=0` 잔량 전부). 실패하면 3초 뒤 한 번 더 한다. 그래도 실패하면 알림에 "HTS에서 취소 필요"를 적는다(−15% 지정가라 체결될 가격은 아니고, 장이 끝나면 사라진다).
  5. 3초 기다린 뒤 다시 조회 4건 — 미체결 목록에서 빠지는지, 주문내역에 취소가 어떻게 남는지
- **결과 파일:** `tr_probe_20261007_{순번}_{TR}_{조건}.json` 22개 + 요약 `tr_probe_20261007_00_summary.json`.
  - 요약에는 호출마다 요청 본문, 응답 코드·메시지, 목록 이름·행 수, **우리 주문번호 행**(가린 사본)을 적는다.
  - 1.6이 확정하려는 것: `ka10075`의 매수·매도 구분 필드(스펙상 `io_tp_nm` "+매수"/"-매도", 지금 코드는 `trde_tp`를 씀), 미체결 잔량 필드(스펙상 `oso_qty`, 지금 코드는 `un_qty`를 찾음), 앱의 지금 파라미터로 미체결이 실제로 보이는가.
- **알림:** 끝나면 `TrProbeCompleted` 이벤트 → 텔레그램 INFO(실패가 하나라도 있으면 WARN)와 로그 한 줄.
- **안전장치:**
  - 키움 주소가 모의 서버(`mockapi.kiwoom.com`)가 아니면 절대 돌지 않는다(ERROR 한 줄).
  - 킬스위치가 켜져 있으면 미루고 다음 분에 다시 본다.
  - 그날 요약 파일이 이미 있으면 다시 돌지 않는다 — 재기동해도 한 번이다.
  - 조회 중 오류(키움 오류 응답·네트워크·유량 대기 초과·파일 저장 실패)는 기록만 하고 다음 단계로 간다. 주문을 낸 뒤에는 반드시 취소까지 간다.
  - `discount-pct`는 5~29만 받는다(가격제한폭 ±30% 안).
  - 계좌번호(`acnt*`)·관리사원번호(`*empno*`) 값은 `****`로 가려 저장한다. 공개 리포에 커밋될 수 있기 때문이다.
- **앱 장부와의 관계:**
  - 이 주문은 주문 경로(RiskGate→trading)를 거치지 않는다. 주문 한도·일련번호·일별 성과 주문 수에 안 잡힌다.
  - 체결통보에서는 "모르는 주문"으로 무시된다(OrderNoticeHandler의 "수동 주문 등으로 추정" 경로). 대사는 DB 주문만 보므로 영향이 없다.
  - 만에 하나 체결되면(현재가 −15%라 사실상 없음) 모의 계좌에 KODEX 200이 1주 늘어난다. 장부는 다음 기동의 잔고 복원 때 맞춰진다.

## 3. 설정(`application.yml`)

```yaml
execution:
  tr-probe:
    enabled: true
    date: 2026-10-07
    at: "10:00"
    symbol: "069500"
    discount-pct: 15
    output-dir: ../docs/measured   # 앱 작업 폴더(app) 기준

monitor:
  market-check:
    enabled: true                  # 09:15 확인, 10:00·14:00 점검
    strategy-run-notice: true      # C3 판단 요약 텔레그램
    max-message-age-seconds: 120
```

- 끄기: `execution.tr-probe.enabled: false`, `monitor.market-check.enabled: false`(재기동 필요).
- 실측을 다른 날 다시 하려면 `date`만 바꾼다.

## 4. 버린 대안

- **Claude 예약 작업으로 장중 점검:** 클라우드 세션이 PC에 닿으려면 데스크톱 앱이 켜져 있어야 한다. 장중에 그것을 보장할 수 없다. 실측 주문은 Claude가 직접 낼 수도 없다.
- **Windows 작업 스케줄러 + PowerShell 실측 스크립트:** 사용자가 작업을 등록해야 하고, 스크립트가 `.env` 키로 토큰을 따로 발급하면 앱 토큰과 엇갈릴 수 있다(8005 재발급 소음). 앱 안에서 하면 같은 토큰·유량 제한기를 쓴다.
- **실측 주문을 앱 주문 경로로:** 주문 장부·일 한도·성과 통계에 실측 주문이 섞인다. 대신 이 실측으로는 1.3 알림 순서와 0.1 미체결 자동 취소가 확인되지 않는다(실제 주문이 생길 때 확인).
- **상태 점검을 매번 텔레그램으로:** 하루 두 번 "정상" 알림은 소음이다. 이상일 때만 보낸다.

## 5. 함정과 주의

- 09:05 뒤에 재기동하면 그날 09:15 점검이 "실행 기록 없음" WARN을 낸다. 실행 기록이 메모리에만 있기 때문이다. 그날 C3는 이미 돌았으니 로그로 확인한다.
- 실측 결과 파일을 커밋하기 전에 한 번 본다. 가리는 키 말고 개인정보 필드는 스펙상 없지만, 모의 서버 응답이 스펙과 다를 수 있다.
- 실측 날짜가 지나면 아무 일도 하지 않는다. 설정을 지우지 않아도 무해하다.
- 실측 중 WS 체결통보 처리 로그(`… 무시`)가 몇 줄 남을 수 있다. 정상이다.

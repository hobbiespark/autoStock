# 코딩 규칙

서비스를 개발/유지보수할 때 따르는 규칙과 정책이다. 널리 검증된 핵심 설계 이론을 대원칙으로 삼는다.
기존 코드와 과거 결정은 유지보수할 때는 따른다.

## 0. 적용 범위와 우선순위

**신규 개발**

1. 사용자의 현재 요청
2. 이 문서
3. 조직 공통 플랫폼 제약: 인증 체계, 공용 라이브러리, 인프라, 전사 규약. 이론과 달라도 따르되, 어댑터로 감싸 도메인 안으로 새지 않게 한다(§2.2 ACL).
4. 기존 서비스의 코드와 관례: 참고만 한다. 이론과 다르면 이론을 따르고, 왜 다르게 했는지 `aiDoc`에 적는다.

**유지보수 (기존 서비스 수정)**

1. 사용자의 현재 요청
2. 그 리포의 기존 코드와 과거 결정(주변 코드, 리포 규칙 문서, 결정을 담은 주석·테스트, `aiDoc`)
3. 이 문서: 기존 관례가 없는 곳에만 쓴다.

기존 관례가 이 문서의 원칙과 다르더라도 임의로 바꾸지 않는다. 결함으로 보이면 고치기 전에 알리고, 사용자가 정한 대로 한다.

**어느 경우든 지키는 것**

- 커밋에 AI 작성 표기를 넣지 않는다(§14).
- `aiDoc`을 작성한다(§15).

원칙끼리 부딪히면 **정확성·보안 → 단순함 → 변경 용이성 → 성능** 순으로 고른다. 이 문서와 다르게 결정했다면 이유를 ADR로 남긴다(§15).

**자주 헷갈리는 규칙 정리**

| 헷갈리는 두 규칙 | 이렇게 한다 |
|---|---|
| 도메인은 프레임워크를 모른다(§3) ↔ 모든 테이블은 JPA 엔티티(§7) | 도메인 엔티티에 JPA 매핑 애너테이션만 허용한다. 모델과 테이블이 크게 다르면 분리한다 |
| 검증은 DTO 한 곳(§2.1) ↔ 도메인이 불변식을 지킨다(§2.2) | 형식(필수, 길이, 패턴)은 DTO, 업무 규칙(상태, 관계, 한도)은 도메인이 맡는다 |
| 없으면 `null`(§2.1) ↔ `null` 대신 빈 컬렉션(§4) | 단일 값은 `null`, 컬렉션은 빈 컬렉션 |
| 빠른 실패(§2.1) ↔ 기능 저하(§2.6) | 잘못된 입력·설정은 실패, 선택 정보의 외부 장애만 저하 |
| 재시도(§2.6) ↔ 모호하면 멈춘다(§2.5) | 결과를 모르는 실패는 멱등 키가 있을 때만 재시도한다 |
| 모르는 필드 무시(§2.4) ↔ 모르는 필드 거부(§10.2.8) | 받는 응답·메시지는 무시, 우리 API 요청은 무시하되 서버가 정하는 필드는 `400` |
| `403`/`404` 구분(§10.2.2) ↔ 존재 여부 은닉(§5.5) | 남의 자원은 `404`, 기능 권한 부족만 `403` |
| 오류를 구체적으로(§16.2) ↔ 열거 공격 방지(§5.5) | 입력 오류는 구체적으로, 인증·계정 오류는 뭉뚱그린다 |
| 심층 방어(§5.1) ↔ 중복 검사 금지(§2.4) | 겹마다 막는 대상이 다르면 둔다. 같은 검사를 반복하지 않는다 |
| 주석은 짧게(§13) ↔ 근거는 상세히(§15) | 코드엔 '왜' 한 줄, 상세는 `aiDoc` |

## 1. 설계 착수 전

- **문제와 용어부터 정한다.** 요구사항, 업무 용어, 용어와 코드 이름의 대응을 먼저 정리한다. 기획 용어가 같은 이름의 컬럼이나 필드를 가리킨다고 단정하지 않는다.
- **경계를 먼저 긋는다.** 이 서비스가 책임지는 것과 책임지지 않는 것, 소유할 데이터, 의존할 외부 시스템을 적는다(컨텍스트 맵).
- **계약을 먼저 쓴다(Contract-First).** 외부에 노출할 API는 구현 전에 스펙(OpenAPI)으로 정의하고, 소비하는 쪽과 합의한다.
- **중요한 결정은 ADR로 남긴다.** 선택지, 고른 것, 이유, 버린 대안을 기록한다(§15).
- **바퀴를 다시 만들지 않는다.** 조직 공용 모듈과 프레임워크가 이미 제공하는 기능(인증, 응답 규약, 헤더 전파, 토큰 발급, 로깅)은 그것을 쓴다.
- **참고 구현은 참고로만 쓴다.** 조직 표준 리포에서 같은 문제를 어떻게 풀었는지 보되, 그대로 복제하지 않고 이 문서의 원칙에 맞는지 따진다.
- **주석, 설정, 문서를 동작으로 믿지 않는다.** 다른 프로젝트에서 복사된 설명, 선언만 있고 구현체가 없는 설정, 낡은 문서가 있다. 코드와 실제 출력으로 확인한다.

## 2. 설계 원칙

### 2.1 기본 원칙

- **SOLID.**
  - 단일 책임(SRP): 클래스 하나가 바뀌는 이유는 하나다.
  - 개방-폐쇄(OCP): 새 기능은 기존 코드를 고치지 않고 확장으로 넣을 수 있게 설계한다.
  - 리스코프 치환(LSP): 구현체는 인터페이스의 약속을 좁히거나 바꾸지 않는다.
  - 인터페이스 분리(ISP): 쓰지 않는 메서드에 의존하게 만들지 않는다.
  - 의존성 역전(DIP): 도메인이 인터페이스(포트)를 소유하고, 인프라가 그것을 구현한다.
- **KISS, YAGNI, 3의 법칙.** 가장 단순한 방법을 먼저 쓴다. 지금 필요 없는 기능, 설정, 확장 지점을 만들지 않는다. 추상화는 같은 패턴이 세 번 나타날 때 만든다. 잘못된 추상화는 중복보다 비싸다.
- **상속보다 합성.** 동작은 위임과 전략 객체로 조합한다. 상속은 진짜 "is-a" 관계일 때만 쓴다.
- **묻지 말고 시켜라(Tell, Don't Ask)와 디미터 법칙.** 객체의 상태를 꺼내 밖에서 판단하지 않고, 객체에 판단을 맡긴다. `a.getB().getC().do()` 같은 사슬을 만들지 않는다.
- **명령-조회 분리(CQS).** 값을 돌려주는 메서드는 상태를 바꾸지 않고, 상태를 바꾸는 메서드는 조회를 겸하지 않는다.
- **빠른 실패(Fail Fast).** 잘못된 입력과 설정은 가장 이른 지점(기동 시점, 경계 입구)에서 거부한다. 기본값으로 덮어 조용히 넘어가지 않는다. 외부 의존 장애로 선택 정보를 못 가져오는 경우는 실패가 아니라 기능 저하로 다룬다(§2.6).
- **최소 놀람 원칙.** 이름이 약속한 일만 한다. 조회 이름을 가진 메서드가 쓰기를 하거나, 설정 하나가 무관한 동작을 바꾸지 않게 한다.
- **단일 진실 원천(SSOT).** 기본값, 매핑, 검증 규칙, 코드값 정의는 한 곳에서만 정한다.
  - 파서나 어댑터가 값을 지어내지 않는다. 입력이 없으면 없음(`null`)을 넘기고 기본값은 도메인 정책 한 곳에서 채운다.
  - 요청 형식 검증(필수, 길이, 패턴)은 요청 DTO 한 곳에서 한다. 서비스에서 같은 검증을 되풀이하지 않는다. 업무 규칙 검증은 도메인이 맡는다(§2.2). 둘은 다른 검증이다.
- **진입 경로 간 정합.** 같은 데이터를 받는 경로가 여럿(단건 API, 일괄 업로드, 내부 호출)이면 같은 도메인 규칙을 거치게 한다. 경로별로 의미가 달라야 하면 모드(enum)로 명시한다.
- **명시적인 것이 암묵적인 것보다 낫다.** 트랜잭션 경계, 시간대, 인코딩, 타임아웃, 풀 크기는 프레임워크 기본값에 맡기지 않고 명시한다.

### 2.2 도메인 설계 (DDD)

- **경계 컨텍스트(Bounded Context).** 같은 단어라도 컨텍스트마다 뜻이 다를 수 있다. 다른 컨텍스트의 모델을 그대로 가져다 쓰지 않고, 경계에서 번역한다.
- **보편 언어(Ubiquitous Language).** 코드 이름은 업무 용어를 따른다. 용어와 코드의 대응은 한 곳(용어표, enum JavaDoc)에 둔다.
- **애그리거트는 일관성 경계다.**
  - 불변식은 애그리거트 루트가 지킨다. 한 트랜잭션에서는 애그리거트 하나만 수정한다. 여러 애그리거트를 바꿔야 하면 도메인 이벤트로 이어 결과적 일관성으로 맞춘다. 업무상 즉시 일관성이 꼭 필요하면 같은 트랜잭션으로 묶고 ADR을 남긴다.
  - 다른 애그리거트는 객체 참조(연관관계 매핑)가 아니라 ID로 참조한다.
  - 애그리거트는 작게 설계한다.
- **풍부한 도메인 모델.** 상태 변경 규칙은 엔티티와 값 객체의 메서드에 둔다. 서비스(애플리케이션 계층)는 흐름만 조율한다. 세터로 상태를 바꾸지 않는다.
- **불변식은 스스로 지킨다.** 도메인 불변식은 엔티티, 값 객체, 도메인 정책이 요구하고, 값이 없다고 조용히 건너뛰지 않는다.
- **값 객체.** 금액, 기간, 식별자 묶음처럼 규칙을 가진 값은 원시 타입 대신 불변 값 객체(`record`)로 표현하고, 생성 시점에 검증한다.
- **도메인 이벤트.** 도메인에서 일어난 의미 있는 사실은 이벤트로 표현하고, 후속 처리(알림, 다른 컨텍스트 반영)는 이벤트를 받아서 한다. 서비스 안에서는 애플리케이션 이벤트(커밋 후 처리)로, 서비스 밖으로는 아웃박스(§2.5)로 보낸다.
- **부패 방지 계층(ACL).** 외부 시스템, 레거시, 조직 공통 플랫폼의 모델·명명·코드값은 어댑터에서 우리 모델로 번역한다. 레거시 명명은 추측하지 말고 실데이터로 확인한다.

### 2.3 아키텍처

- **헥사고날(포트와 어댑터)과 클린 아키텍처.**
  - 도메인과 유스케이스가 중심에 있고 웹, DB, 메시징, 외부 API는 바깥의 어댑터다.
  - 의존은 바깥에서 안쪽으로만 향한다. 도메인 코드는 프레임워크, HTTP, SQL을 모른다.
  - 들어오는 포트(유스케이스 인터페이스)와 나가는 포트(저장소, 외부 연동 인터페이스)를 도메인·애플리케이션 계층이 소유한다.
- **모듈러 모놀리스로 시작한다(Monolith First).** 한 서비스 안에서 모듈 경계와 의존 방향을 지킨다. 서비스 분리는 독립 배포, 독립 확장, 팀 경계가 실제로 필요해졌을 때 한다.
- **콘웨이 법칙.** 서비스 경계는 팀과 책임 경계를 따른다. 기술적 편의만으로 경계를 정하지 않는다.
- **CQRS는 필요한 만큼만 쓴다.** 명령과 조회의 모델·서비스를 나누는 것은 기본으로 한다. 저장소까지 나누는 것(읽기 전용 모델, 복제본)은 조회 요구가 명령 모델과 크게 다를 때 도입한다.

### 2.4 서비스 경계 (MSA)

- **높은 응집, 낮은 결합.** 함께 바뀌는 것은 한 서비스에 두고, 서비스끼리는 공개된 계약(API, 이벤트)으로만 만난다. 다른 서비스의 내부 구현, 테이블, 캐시 키에 기대지 않는다.
- **서비스별 데이터베이스(Database per Service).**
  - 서비스는 자기 스키마를 소유한다. 다른 서비스의 테이블을 직접 읽거나 쓰지 않는다.
  - 다른 서비스의 데이터가 필요하면 API로 조회하거나, 이벤트로 받아 자기 읽기 모델에 둔다.
  - 조직 사정으로 공유 DB를 써야 하면 ADR로 남기고, 테이블 소유자를 정하고, 소유자의 규약(시간대, 코드값, 감사 컬럼)을 따른다.
- **분산 모놀리스를 피한다.**
  - 한 요청이 여러 서비스를 동기로 줄줄이 부르는 사슬을 만들지 않는다.
  - 여러 서비스를 늘 함께 배포해야 하는 변경을 만들지 않는다. 계약 변경은 Expand-Contract로 한다(§2.8).
- **통신 방식을 목적에 맞게 고른다.** 즉시 결과가 필요한 조회는 동기 API로 한다. 기다릴 필요가 없는 후속 처리, 대량 작업, 다른 서비스에 알리는 일은 비동기(작업 접수 후 상태 조회, 이벤트)로 한다.
- **신뢰 경계는 입구에서 정한다.**
  - 인증은 경계(게이트웨이, BFF)에서 한다.
  - 인가(이 사용자가 이 자원에 접근할 수 있는가)는 자원을 소유한 서비스가 최종 판단한다.
  - 내부망이라고 무조건 믿지 않는다(제로 트러스트). 서비스 간 호출도 호출자를 식별한다.
- **관대한 수신자(Tolerant Reader).** 우리가 다른 서비스의 응답이나 메시지를 받을 때는 필요한 필드만 읽고, 모르는 필드는 무시한다. 보내는 쪽은 계약을 엄격하게 지킨다. 우리 API가 받는 요청은 §10.2.8을 따른다.

### 2.5 분산 일관성

- **분산 트랜잭션(2PC)을 쓰지 않는다.** 서비스 경계를 넘는 원자성을 DB 트랜잭션으로 얻으려 하지 않는다.
- **결과적 일관성을 명시한다.** 어떤 데이터가 언제까지 어긋날 수 있는지, 누가 그것을 맞추는지(재시도, 대사 배치)를 설계에 적는다.
- **보상(Saga).** 여러 서비스에 걸친 작업은 단계마다 되돌리는 보상 동작을 정한다. 보상할 수 없는 단계(외부 발송, 결제 확정)는 가장 마지막에 둔다.
- **트랜잭셔널 아웃박스.** DB 변경과 외부 발행(이벤트, 메일, 외부 API)을 함께 보장해야 하면, 같은 트랜잭션에서 발행할 내용을 아웃박스 테이블에 적고 별도 발행기가 읽어 보낸다. "커밋 후 발송"도 "발송 후 커밋"도 유실이나 중복을 만든다.
- **멱등성.** 쓰기 API, 메시지 수신, 재처리는 같은 요청이 두 번 와도 결과가 같게 만든다. 멱등 키, 유니크 제약, 상태 전이 조건으로 막는다.
- **상태가 모호하면 멈춘다.** 성공인지 실패인지 알 수 없는 작업(응답 전 타임아웃 등)은 멱등 키로 중복을 막을 수 있을 때만 재시도한다. 막을 수 없으면 보류하고, 사람이 판단할 수 있게 기록한다.

### 2.6 복원력

- **모든 원격 호출에는 연결·응답 타임아웃을 둔다.** 무한 대기를 기본값으로 두지 않는다.
- **재시도는 멱등 호출에만 건다.** 지수 백오프와 지터를 붙이고 횟수에 상한을 둔다. 호출 계층마다 재시도를 겹쳐 걸지 않는다(재시도 폭증). 전체를 다시 하게 되는 루프 호출에는 걸지 않는다.
- **서킷 브레이커.** 반복 실패하는 하위 서비스는 차단하고 빠르게 실패한다. 임계값(최소 호출 수 등)이 실제 트래픽에서 열리는 값인지 확인한다. 서킷이 열려 있다고 재시도 예산이나 작업 상태를 소모해 영구 누락이 생기지 않게 한다.
- **격벽(Bulkhead).** 스레드 풀, 커넥션 풀, 비동기 실행기는 용도별로 나누고 상한을 둔다. 상한 없는 실행기를 쓰지 않는다.
- **폴백과 우아한 기능 저하.** 부가 정보를 못 가져오면 핵심 기능은 살리고 부가 정보만 비운다. 폴백이 잘못된 데이터를 정상처럼 보이게 만들지 않게 한다.
- **백프레셔와 레이트 리밋.** 대량 작업과 공개 엔드포인트에는 처리량 상한(건수, 동시 실행 수, 요청 빈도)을 설정값으로 두고, 넘치면 거부하거나 줄을 세운다.

### 2.7 운영 친화 (12-Factor, 관측성)

- **설정은 환경에서 주입한다.** 환경마다 다른 값은 환경변수나 설정 서버로 주입하고, 코드에 환경 분기를 넣지 않는다.
- **프로세스는 무상태로 만든다.** 세션, 인증 핸드셰이크 상태, 작업 상태는 파드 메모리가 아니라 공유 저장소(DB, Redis)에 둔다. 인스턴스가 여러 개이거나 재시작돼도 동작해야 한다.
- **빨리 뜨고 깨끗이 내린다.** 종료 신호를 받으면 진행 중인 요청과 작업을 마치거나 안전하게 되돌린다(graceful shutdown). 중단된 작업은 다음 실행이 회수할 수 있게 상태를 남긴다.
- **개발과 운영을 같게 유지한다.** 로컬·테스트·운영의 DB 엔진, 설정 구조, 의존성 버전을 같게 한다.
- **로그는 이벤트 스트림이다.** 표준 출력으로 구조화 로그(JSON)를 내보내고, 수집은 플랫폼에 맡긴다.
- **관측성의 세 축을 갖춘다.**
  - 로그: 구조화하고, 추적 ID를 싣는다.
  - 메트릭: 요청 수, 오류율, 지연(RED)과 자원 사용량을 노출한다.
  - 추적: 추적 ID를 서비스 경계 너머로 전파한다(W3C Trace Context). 응답에도 같은 ID를 싣는다.
- **헬스 체크는 준비(readiness)와 생존(liveness)을 나눈다.** 외부 의존 장애로 생존 검사가 실패해 파드가 재시작되는 일이 없게 한다.
- **실패는 알림이 가는 경로로 남긴다.** 로그만 남기는 스텁 알림기를 운영에 두지 않는다.
- **스케줄 작업은 분산 잠금으로 한 번만 실행되게 한다.**

### 2.8 진화적 변경

- **Expand-Contract(병행 변경).** API, 스키마, 설정을 바꿀 때는 새것을 추가하고(Expand), 사용처를 옮기고(Migrate), 옛것을 지운다(Contract). 한 번의 배포로 양쪽을 동시에 바꾸지 않는다.
- **스트랭글러 피그.** 레거시를 대체할 때는 한 번에 갈아엎지 않는다. 새 경로를 옆에 세우고 기능 단위로 트래픽을 옮긴다.
- **되돌릴 수 있게 만든다.** 위험한 변경에는 롤백 경로(기능 토글, 이전 버전 병행, 역방향 마이그레이션)를 두고, 그 방법을 `aiDoc`에 적는다.
- **밖으로 나가는 값은 나가기 전에 확정한다.** 코드값과 식별자가 저장·복제되어 다른 시스템으로 퍼진 뒤에는 바꾸는 비용이 커진다. 공개 전에 실데이터로 검증한다.

## 3. 프로젝트 구조

- **패키지는 기능(컨텍스트) 우선, 그 안에서 계층으로 나눈다.** 예: `order/domain`, `order/application`, `order/adapter/in/web`, `order/adapter/out/persistence`.
- **계층 책임.**
  - 웹 어댑터(컨트롤러): 요청 변환, 검증 애너테이션 적용, 유스케이스 호출, 응답 변환만 한다.
  - 애플리케이션 서비스: 트랜잭션 경계와 흐름 조율을 맡는다. 도메인 규칙을 직접 구현하지 않는다.
  - 도메인: 엔티티, 값 객체, 도메인 서비스, 포트 인터페이스를 둔다. 프레임워크 의존이 없다. 단, 엔티티의 JPA 매핑 애너테이션(`jakarta.persistence`)은 허용한다. Spring, 웹, 쿼리 빌더 의존은 두지 않는다. 도메인 모델과 테이블 구조가 크게 다르면 영속성 엔티티를 어댑터에 따로 두고 변환한다.
  - 영속성·외부 어댑터: 포트를 구현한다.
- **모듈 의존 방향을 빌드로 강제한다.** 멀티 모듈이나 아키텍처 테스트(ArchUnit)로 역방향 의존을 막는다.
- **조립은 명시적으로 한다.** 컴포넌트 스캔 범위를 넓혀서 문제를 해결하지 않고, 설정 클래스로 필요한 빈을 가져온다.
- **외부 의존은 포트 뒤에 둔다.** 실제 어댑터와 로컬·테스트용 구현(Stub, Fake)을 프로파일로 바꿔 끼울 수 있게 한다.
- **엔티티를 API 응답으로 내보내지 않는다.** 계층 사이는 전용 DTO로 넘기고, 반환 타입을 `Object`로 두지 않는다.

## 4. Java 스타일

- **불변을 기본으로 한다.** DTO, 커맨드, 결과, 값 객체는 `record`로 쓴다. `@Setter`, `@Data`를 쓰지 않는다.
- **의존성은 `final` 필드와 생성자 주입으로 받는다.** 필드 주입, 세터 주입을 쓰지 않는다.
- **엔티티의 기본 생성자는 `protected`로 막고, 생성은 의도가 드러나는 팩토리 메서드로 한다.**
- **`Optional`은 반환값에만 쓴다.** 파라미터나 필드에 두지 않는다.
- **컬렉션은 `null` 대신 빈 컬렉션을 반환한다.** 단일 값이 없음을 나타낼 때만 `null`이나 `Optional`을 쓴다.
- **공개 범위는 최소로 둔다.** 보조 메서드는 `private`이 기본이다. 테스트하려고 범위를 넓히지 않는다.
- **긴 메서드는 단계 이름을 가진 메서드로 나눈다.** 주석으로 구간을 나누지 않는다. 단, 나누면 같은 타입의 위치 인자가 많아져 순서를 바꿔도 컴파일이 되는 경우에는 값 객체로 묶거나 나누지 않는다.
- **결과를 쓰는 곳을 한 군데로 모은다.** 판정 결과를 값(`sealed interface` 등)으로 모은 뒤 한 곳에서 응답을 쓴다.
- **분기는 타입으로 표현한다.** 상태별 동작은 `enum`의 메서드, `sealed` 계층, 패턴 매칭 `switch`로 쓰고, 문자열 비교 분기를 늘어놓지 않는다.

## 5. 보안과 시큐어코딩

**기준**: 행정안전부 「소프트웨어 보안약점 진단가이드」(구현 단계 보안약점 7개 분류)를 뼈대로 삼고, OWASP Top 10, OWASP ASVS, CWE Top 25로 보완한다. 조직 보안 지침이 있으면 함께 따른다.

### 5.1 설계 원칙

- **기본값을 안전하게 둔다(Secure by Default).** 새 엔드포인트는 인증 필요가 기본이고, 공개는 명시적으로 연다. 보안 헤더, TLS, 쿠키 속성도 안전한 쪽이 기본이다.
- **최소 권한.** DB 계정, 서비스 토큰, 클라우드 역할, 파일 권한에는 필요한 권한만 준다. 조회 전용 서비스는 조회 전용 계정을 쓴다.
- **심층 방어.** 한 겹이 뚫려도 다음 겹이 막도록 경계, 서비스, DB 제약에 각각 알맞은 방어를 둔다. 겹마다 무엇을 막는지 정하고, 이유 없는 중복은 두지 않는다(§2.4).
- **fail-closed.** 암호화, 복호화, 인가, 격리 판정이 실패하면 거부한다. 평문 반환, 통과, 자동 등록으로 떨어지지 않는다.
- **끝에서 끝까지 확인한다.** 각 계층이 "자기 몫은 맞다"여도 합치면 구멍일 수 있다. 여러 계층을 지나는 요청은 한 번 끝까지 따라가 보고, 권한 검사는 관리자가 아닌 계정으로 시험한다.
- **위협 모델링.** 인증, 결제, 개인정보, 파일 업로드, 외부 연동을 다루는 기능은 설계 단계에서 STRIDE 관점으로 위협을 적고, 대응을 `aiDoc`에 남긴다.

### 5.2 입력 데이터 검증 및 표현

모든 외부 입력(요청 파라미터, 헤더, 쿠키, 파일, 외부 API 응답, 메시지)은 신뢰하지 않는다. 검증은 서버에서 하고, 클라이언트 검증은 편의로만 본다.

- **화이트리스트로 검증한다.** 형식, 길이, 범위, 허용 값 목록으로 받는다. 블랙리스트(금지 문자 제거)에 기대지 않는다. 검증 전에 정규화(유니코드, 경로, 인코딩)를 먼저 한다.
- **SQL 삽입**: 바인딩 파라미터로만 쿼리를 만든다. 문자열 이어 붙이기, MyBatis `${}`, 동적 `ORDER BY` 컬럼명 직접 삽입을 쓰지 않는다. 동적 식별자는 화이트리스트에서 고른다.
- **명령어·코드 삽입**: 외부 입력으로 OS 명령, 스크립트, 표현식(SpEL, OGNL), 템플릿을 실행하지 않는다. 꼭 필요하면 인자 배열로 넘기고 셸을 거치지 않는다.
- **경로 조작**: 파일 경로에 외부 입력을 쓰지 않는다. 써야 하면 허용 목록에서 고르고, 정규화한 경로가 기준 디렉터리 안에 있는지 확인한다.
- **XSS**: 백엔드가 HTML을 만들면(서버 렌더링, 이메일 템플릿) 출력 위치에 맞게 인코딩하는 템플릿 엔진을 쓴다. 리치 텍스트를 받아 저장하면 허용 태그 목록으로 정제한다. JSON 응답은 `Content-Type: application/json`으로 보낸다.
- **SSRF**: 서버가 외부 URL을 가져오면 스킴(http/https), 호스트 허용 목록, 사설·루프백·메타데이터 주소 차단, 리다이렉트 재검증을 적용한다.
- **XXE와 역직렬화**: XML 파서는 외부 엔티티와 DTD를 끈다. 신뢰하지 않는 데이터를 Java 기본 직렬화나 다형성 타입 정보가 켜진 JSON으로 역직렬화하지 않는다.
- **오픈 리다이렉트**: 리다이렉트 목적지는 허용 목록이나 상대 경로만 받는다.
- **HTTP 응답 분할과 로그 위조**: 헤더와 로그에 넣는 외부 입력은 개행 문자를 제거하거나 인코딩한다.
- **파일 업로드**: 크기 상한을 두고, 형식은 확장자가 아니라 내용 시그니처로 확인하고, 저장 파일명은 서버가 새로 짓고, 실행 불가능한 저장소(웹 루트 밖, 객체 저장소)에 둔다. 압축 파일은 압축 해제 크기와 파일 수에 상한을 둔다(압축 폭탄).
- **정규식 서비스 거부(ReDoS)**: 외부 입력에 쓰는 정규식은 역추적이 폭발하지 않게 쓰고, 입력 길이에 상한을 둔다.
- **대량 할당(Mass Assignment)**: 요청 DTO를 엔티티에 통째로 바인딩하지 않는다. 받을 필드만 가진 전용 DTO를 쓴다.
- **정수 오버플로와 숫자 범위**: 수량, 금액, 페이지 크기처럼 계산에 쓰이는 숫자는 범위를 검증한다.

### 5.3 보안 기능

- **인증**
  - 인증은 조직 공통 인증 체계(IAM, OAuth 2.0/OIDC)를 쓰고, 자체 비밀번호 저장소를 만들지 않는다.
  - 자체 저장이 불가피하면 비밀번호는 적응형 단방향 해시(Argon2id, bcrypt)로 저장한다.
  - 로그인, 비밀번호 찾기, 본인인증처럼 인증 전에 열린 경로에는 시도 횟수 제한을 둔다.
- **인가**
  - 사용자·테넌트·소유자 ID, 권한, 리다이렉트 목적지는 요청 파라미터가 아니라 검증된 인증 컨텍스트에서 꺼낸다(IDOR 방지). 소유 범위 검사는 경로 변수, 쿼리, 본문 중 어느 자리로 오든 한다.
  - 인가는 자원을 소유한 서비스가 최종 판단한다(§2.4). URL 패턴만으로 끝내지 않고 대상 자원 단위로 확인한다.
  - 관리 기능은 일반 기능과 경로·권한을 분리한다.
- **암호화**
  - 검증된 표준 알고리즘과 라이브러리만 쓴다. 대칭키는 AES-GCM, 해시는 SHA-256 이상을 쓰고, DES, RC4, MD5, SHA-1, ECB 모드는 쓰지 않는다. 암호 알고리즘을 직접 구현하지 않는다.
  - 난수는 보안 용도에 `SecureRandom`을 쓰고 `Random`, `Math.random`을 쓰지 않는다.
  - 키는 코드와 설정 파일에 두지 않고 키 관리 수단(KMS, Vault)에 둔다. 키 교체가 가능하게 암호문에 키 버전을 싣는다.
  - 전송 구간은 TLS 1.2 이상으로 암호화한다. 인증서 검증을 끄지 않는다.
- **비밀 값은 어떤 환경이든 리포에 넣지 않는다.** 비밀 관리 수단(Secret, Vault)이나 배포 시 환경변수로 주입한다. 로컬용 값은 커밋되지 않는 파일에 둔다.
- **개인정보는 저장·전송·표시 단계별로 보호한다.**
  - 수집은 목적에 필요한 최소한만 한다.
  - 저장 시 고유식별정보, 비밀번호, 바이오정보 등 법령상 암호화 대상은 암호화한다.
  - 목록 응답은 마스킹하고, 원본은 권한이 있는 단건 조회에서만 준다.
  - 로그에는 남기지 않는다.
  - 보관 기간이 지나면 파기한다.
  - 개인정보 조회·다운로드는 누가 언제 무엇을 봤는지 접속 기록을 남긴다.
- **쿠키와 세션**
  - 인증 자격 쿠키는 `HttpOnly`, `Secure`, `SameSite`를 붙이고, 도메인 범위는 가장 좁게 둔다.
  - 로그인에 성공하면 세션 식별자를 새로 발급한다(세션 고정 방지).
  - 세션과 토큰에는 만료를 두고, 로그아웃 때 서버 쪽에서도 무효화한다.
- **CSRF**: 쿠키로 인증하는 상태 변경 요청은 CSRF 토큰이나 `SameSite`와 출처 검사로 막는다.
- **CORS**: 허용 출처는 환경별로 목록에 명시한다. 자격 증명을 허용하면서 `*`나 요청 출처를 그대로 되돌려 주지 않는다.
- **보안 응답 헤더**: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy`(HTML 응답), `Referrer-Policy`, 캐시 금지(민감 응답)를 둔다.
- **감사 로그**: 로그인, 권한 변경, 개인정보 접근, 관리 기능 실행은 행위자, 대상, 시각, 결과, 실제 클라이언트 IP를 남긴다. 클라이언트 IP는 신뢰하는 프록시가 붙인 값만 쓴다(위조 가능한 `X-Forwarded-For` 맨 앞 값을 그대로 믿지 않는다).

### 5.4 시간 및 상태

- **확인과 사용 사이의 경쟁 조건(TOCTOU)을 막는다.** "검사 후 변경"은 같은 트랜잭션과 잠금, 또는 조건부 갱신(`UPDATE ... WHERE 상태 = ?`)으로 원자적으로 한다(§7).
- **1회용 토큰과 인증 상태는 한 번만 쓰이게 한다.** 사용과 소멸을 원자적으로 처리하고, 작업이 성공한 뒤에 소멸시킨다.
- **종료되지 않는 반복과 재귀를 막는다.** 외부 입력으로 반복 횟수나 재귀 깊이가 정해지는 곳은 상한을 둔다.
- **공유 자원은 스레드 안전하게 쓴다.** 싱글톤 빈에 요청별 상태를 필드로 두지 않는다.

### 5.5 에러 처리

- **내부 정보를 밖으로 내보내지 않는다.** 예외 원인, 스택, SQL, 키 ID, 서버 경로와 버전은 서버 로그에만 남기고, 클라이언트에는 일반 메시지와 에러 코드만 준다(§6).
- **열거 공격에 쓰일 차이를 만들지 않는다.** 계정 존재 여부, 권한 없음과 없음의 차이처럼 공격자에게 정보가 되는 차이는 응답 내용과 응답 시간으로 드러내지 않는다. 남의 자원 접근은 `404`로 답하고(§10.2.2), 로그인·계정 찾기 실패는 원인을 가르지 않는 한 가지 문구로 답한다.
- **예외를 삼키지 않는다.** 보안 판정 중 예외는 거부로 처리한다(fail-closed).

### 5.6 코드 오류

- **`null` 역참조, 자원 누수를 막는다.** 스트림, 커넥션, 파일은 try-with-resources로 닫는다.
- **임시 파일은 안전하게 만들고 반드시 지운다.** 예측 가능한 이름을 쓰지 않고, 권한을 최소로 둔다.
- **민감 데이터는 쓴 뒤 오래 들고 있지 않는다.** 비밀번호와 키는 가능하면 `char[]`, `byte[]`로 다루고 쓴 뒤 지운다.

### 5.7 캡슐화

- **디버그 코드와 테스트용 엔드포인트를 운영에 남기지 않는다.** 불가피하면 프로파일로 운영에서 비활성화하고, 기동 시 운영 프로파일에 없음을 검사한다.
- **운영 관리 경로(actuator, API 문서)는 최소만 열고 인증이나 네트워크로 막는다.** 헬스 체크만 공개한다.
- **응답에 필요 이상의 필드를 싣지 않는다.** 내부 ID, 다른 사용자 정보, 비공개 속성이 응답 DTO로 새지 않게 한다.
- **가변 내부 객체를 그대로 반환하지 않는다.** 컬렉션은 불변 사본으로 넘긴다.

### 5.8 API 오용

- **보안 판정에 DNS 조회 결과나 `Referer`, `User-Agent` 같은 위조 가능한 값을 쓰지 않는다.**
- **보안 관련 설정을 끄는 API를 쓰지 않는다.** 인증서 검증 끄기, 모든 호스트 허용, CSRF 전역 비활성화가 여기에 해당한다. 꼭 필요하면 범위를 최소로 좁히고 ADR로 남긴다.
- **취약한 API를 쓰지 않는다.** 폐기 예정 암호 API, 안전하지 않은 역직렬화 API가 여기에 해당한다.

### 5.9 공급망과 점검

- **의존성 취약점을 빌드에서 검사한다(SCA).** 알려진 취약점이 있는 버전은 올리거나, 영향이 없다는 근거를 남긴다.
- **정적 분석(SAST)을 CI에 넣는다.** 시큐어코딩 규칙 위반은 머지 전에 잡는다.
- **컨테이너 이미지는 최소 베이스 이미지를 쓰고, 루트가 아닌 사용자로 실행한다.**
- **보안 결함은 일반 결함보다 먼저 고친다.** 조치할 수 없는 항목은 위험 수용 근거와 담당을 기록한다.

## 6. 예외와 로깅

- **예외는 원인별로 나눈다.** 클라이언트 잘못(4xx)과 서버·하위 시스템 문제(5xx)를 다른 타입으로 던진다. 하위 서비스가 우리 자격을 거절한 경우는 호출자 잘못이 아니므로 4xx로 넘기지 않고 `502`로 답한다(§10.2.2).
- **에러 응답 형식을 하나로 정한다.** 조직 공통 규약이 있으면 따르고, 없으면 RFC 9457(Problem Details)을 쓴다. 기계가 읽는 에러 코드와 사람이 읽는 메시지를 나눈다.
- **에러 코드는 enum 한 곳에 모은다.** 선언과 실제 사용이 어긋나지 않는지 테스트로 검사한다.
- **전역 예외 처리는 한 곳에서 한다.** 컨트롤러마다 try-catch로 응답을 만들지 않는다.
- **예상된 오류는 WARN, 예상 못 한 오류만 ERROR로 남긴다.** 예상된 오류가 장애 알림으로 새지 않게 한다.
- **실패를 삼키지 않는다.** 빈 catch, 로그만 찍고 성공처럼 반환하는 코드를 만들지 않는다. 확인을 먼저 하고 변경은 나중에 한다.
- **로그에 비밀과 개인정보를 남기지 않는다.** 토큰, 비밀번호, 비밀번호가 든 접속 URL, 암호문, 개인정보가 대상이다. "DEBUG라 괜찮다"는 전제는 성립하지 않는다. 라이브러리가 자동으로 찍는 로그도 확인한다.
- **외부 응답 본문을 통째로 로그에 찍지 않는다.** 상태 코드와 오류 코드만 남기고, IP와 서명 URL은 마스킹한다.
- **로그는 구조화한다.** 메시지 문자열에 값을 이어 붙이지 않고 키-값으로 남긴다. 추적 ID를 모든 로그에 싣는다.

## 7. 영속화와 트랜잭션

- **모든 테이블은 ORM 엔티티를 가진다.** 엔티티 없이 수기 SQL로만 다루는 테이블을 만들지 않는다.
- **추상화 수준이 높은 수단부터 쓴다.**
  - 단건·소량 CRUD는 리포지토리 메서드로 한다.
  - 동적 조건, 조인, DTO 프로젝션, 조건부 일괄 수정은 타입 안전 쿼리 빌더(QueryDSL 등)로 한다.
  - 수기 SQL은 ORM으로 표현하면 엔티티 왕복이 생기는 벌크 작업에만 쓴다. 왜 벌크인지 주석을 한 줄 남긴다.
- **표준 SQL을 우선한다.** 벤더 전용 기능(`SKIP LOCKED`, 윈도 함수 확장 등)은 명확한 이득이 있을 때 ADR을 남기고 쓴다. 테스트는 운영과 같은 DB 엔진으로 하므로(§12) 이식성을 핑계로 운영 SQL과 테스트 SQL을 나누지 않는다.
- **트랜잭션 경계를 명시한다.**
  - 트랜잭션은 애플리케이션 서비스에서 연다. 리포지토리가 알아서 여는 동작에 기대지 않는다.
  - 조회는 읽기 전용 트랜잭션으로 한다.
  - 외부 API 호출을 트랜잭션 안에 넣지 않는다. 커넥션을 쥔 채 기다리면 풀이 고갈된다.
  - 트랜잭션은 짧게 유지한다. 뷰 렌더링까지 영속성 컨텍스트를 끌고 가지 않는다(`open-in-view: false`).
- **동시성은 명시적으로 제어한다.**
  - 갱신 충돌이 드문 곳은 낙관적 잠금(`@Version`)을 쓴다.
  - 작업 큐 선점은 같은 트랜잭션 안에서 행 잠금(`SELECT ... FOR UPDATE`)으로 한다. 잠금은 ID 오름차순으로 걸어 데드락을 피한다. 동시 작업자가 많아 `SKIP LOCKED`가 필요하면 위 벤더 기능 규칙대로 ADR을 남기고 쓴다.
  - 드라이버의 배치 반환 행수로 소유권을 판정하지 않는다. 드라이버 설정에 따라 믿을 수 없다.
- **N+1을 피한다.** 페이지를 먼저 확정하고 필요한 값을 `IN` 한 번으로 모아 온다. 큰 `IN` 목록은 청크로 나눈다.
- **필터는 페이징 전에 건다.** 페이징 뒤에 거르면 페이지 크기와 총계가 틀어진다.
- **조인으로 행이 불어나지 않는지 확인한다.** 1:N 조인과 중복 행이 있는 연결 테이블을 주의한다.
- **대량 데이터는 스트리밍, 키셋 페이지네이션, 청크 단위로 처리한다.** 전체를 메모리에 올리지 않는다.
- **무결성은 DB 제약으로도 지킨다.** 유니크, NOT NULL, FK(같은 서비스 스키마 안), CHECK 제약을 건다. 애플리케이션 검사만 믿지 않는다.
- **감사 컬럼(생성·수정 시각과 주체)을 모든 테이블에 표준으로 둔다.**

## 8. 스키마 변경

- **스키마는 버전 관리되는 마이그레이션(Flyway, Liquibase)으로 리포에 둔다.** 운영은 `ddl-auto: none` 또는 `validate`로 두고, 앱이 스키마를 만들지 않는다.
- **마이그레이션은 앞으로만 간다.** 이미 적용된 파일은 고치지 않고 새 파일을 추가한다.
- **파괴적 변경은 Expand-Contract로 나눈다(§2.8).** 개명은 "새 컬럼 추가 → 이중 쓰기·백필 → 읽기 전환 → 옛 컬럼 삭제" 순서로 배포를 나눈다.
- **데이터가 쌓인 테이블을 지우고 다시 만드는 스크립트를 운영에 돌리지 않는다.**
- **스키마 비교는 이름 단위로 양방향 대조한다.** 개수 비교는 개명을 잡지 못한다. 인덱스는 구성 컬럼까지 비교한다.
- **다른 시스템이 의존하는 테이블(복제, 공유 잠금 등)은 코드 참조 여부와 무관하게 보호한다.** 의존 여부는 코드가 아니라 등록 문서로 판단한다.
- **문자셋과 정렬 규칙(collation)은 스키마 단위로 하나로 통일한다.** 일괄 변경이 컬럼 단위 설정을 덮어쓰는지 확인한다.

## 9. 시간과 시간대

- **시각은 UTC 순간값으로 저장한다.** 앱에서는 `Instant`나 `OffsetDateTime`을 쓰고, 날짜를 문자열로 들고 다니지 않는다.
- **업무 시간대 변환은 경계에서 한다.** 표시, 보고서, "오늘"의 판정처럼 업무 시간대가 필요한 곳에서만 변환한다.
- **날짜 경계(자정, 월초)는 업무 시간대로 계산한 뒤 UTC로 바꿔 조회한다.** UTC 자정을 업무 날짜 경계로 쓰지 않는다.
- **이중 변환을 하지 않는다.** DB 세션 시간대, JDBC 시간대, JVM 시간대, 직렬화 시간대를 명시하고, 어느 층에서 변환하는지 한 곳에 적는다. SQL에서 컬럼을 시간대 함수로 감싸면 인덱스도 타지 않는다.
- **날짜만 있는 값(생일, 계약일)은 `LocalDate`로 다룬다.**
- **현재 시각은 주입받는 `Clock`에서 얻는다.** 테스트에서 시각을 고정할 수 있게 한다.
- 다른 서비스 소유 테이블을 공유하는 예외 상황(§2.4)에서는 소유자의 저장 규약을 따른다.

## 10. API 설계

### 10.1 방식 선택

- **REST가 기본이다.** 서비스가 외부와 다른 서비스에 여는 API는 REST로 만든다.
- **GraphQL은 조건이 맞을 때 도입한다.** 다음에 해당하면 검토하고, 도입 결정은 ADR로 남긴다.
  - 화면마다 필요한 필드 조합이 크게 달라 REST 엔드포인트가 화면 수만큼 늘어난다.
  - 한 화면이 여러 리소스·서비스를 한 번에 모아야 해 왕복이 많다.
  - 여러 클라이언트(웹, 앱, 파트너)가 같은 데이터를 서로 다른 모양으로 쓴다.
- **GraphQL의 자리는 클라이언트 쪽 집계 계층(BFF, API 조합)이다.** 서비스 사이 내부 통신은 REST(또는 이벤트)로 한다. GraphQL 서버가 하위 서비스를 부르는 구조는 §2.4의 동기 사슬이 되기 쉬우므로, 묶어 호출하고 타임아웃을 걸고 부분 실패를 허용한다(§10.3).
- **두 방식을 함께 쓰면 도메인 로직은 하나만 둔다.** REST 컨트롤러와 GraphQL 리졸버는 둘 다 같은 유스케이스(들어오는 포트)를 호출하는 어댑터다(§2.3). 리졸버에 업무 규칙을 넣지 않는다.
- **계약을 먼저 쓴다.** REST는 OpenAPI, GraphQL은 SDL 스키마를 구현보다 먼저 정의하고 리뷰한다(§1).

### 10.2 REST

**성숙도 목표**: Richardson 성숙도 모델 Level 2(리소스 + HTTP 의미)는 필수다. Level 3(하이퍼미디어)은 §10.2.6의 범위에서 적용한다.

#### 10.2.1 리소스 모델링

- **URL은 리소스(명사)를 가리키고, 동작은 HTTP 메서드로 표현한다.** 경로에 동사(`/getOrders`, `/createOrder`)를 넣지 않는다.
- **이름 규칙**: 경로는 kebab-case 복수형 명사(`/training-centers`), JSON 필드는 camelCase로 쓴다. 한 API 안에서 섞지 않는다.
- **계층은 소유 관계가 있을 때만 중첩하고, 두 단계를 넘기지 않는다.** 예: `/orders/{orderId}/items`. 더 깊어지면 최상위 리소스와 필터로 푼다.
- **CRUD로 표현되지 않는 동작은 리소스로 모델링한다.**
  - 상태 전이는 하위 리소스 생성으로 표현한다. 예: 취소는 `POST /orders/{id}/cancellation`.
  - 그래도 부자연스러우면 제한적으로 `POST /orders/{id}:cancel` 같은 사용자 정의 메서드를 쓰고, 한 API 안에서 방식을 통일한다.
- **식별자는 불투명하게 다룬다.** 클라이언트가 ID의 구조나 순서에 의존하지 않게 하고, 내부 순번을 노출해 열거가 가능해지면 안 되는 리소스는 추측 불가능한 ID를 쓴다.

#### 10.2.2 HTTP 의미

- **메서드의 성질을 지킨다.**

  | 메서드 | 용도 | 안전 | 멱등 |
  |---|---|---|---|
  | `GET` | 조회 | 예 | 예 |
  | `POST` | 생성, 동작 실행 | 아니오 | 아니오 (멱등 키로 보완) |
  | `PUT` | 전체 교체 | 아니오 | 예 |
  | `PATCH` | 부분 수정 | 아니오 | 보장 안 함 |
  | `DELETE` | 삭제 | 아니오 | 예 |

  `GET`은 상태를 바꾸지 않는다. `GET`에 본문을 싣지 않는다.
- **상태 코드는 의미대로 쓴다.**
  - 성공: `200` 조회·수정, `201` 생성(+ `Location` 헤더), `202` 비동기 접수, `204` 본문 없음
  - 클라이언트 오류: `400` 형식 오류, `401` 미인증, `403` 권한 없음, `404` 없음, `409` 상태 충돌, `412` 전제 조건 실패, `415` 미지원 형식, `422` 의미상 처리 불가, `429` 요청 과다(+ `Retry-After`)
  - 서버 오류: `500` 내부 오류, `502` 하위 서비스 오류, `503` 일시 불가(+ `Retry-After`), `504` 하위 서비스 시간 초과
- **`403`과 `404`를 구분하는 기준.** 남의 자원(존재 여부 자체가 정보인 것)에 접근하면 `404`로 답한다. `403`은 자원이 있다는 것이 이미 알려진 상태에서 기능 권한이 부족할 때만 쓴다(§5.5).
- **조직 공통 응답 봉투가 있으면 따른다(§0).** 그래도 HTTP 상태 코드는 의미대로 쓴다. 실패를 `200`에 담아 보내지 않는다.
- **에러 본문은 §6의 형식(조직 규약 또는 RFC 9457)으로 통일한다.** 필드 검증 오류는 어느 필드가 왜 틀렸는지 목록으로 준다.

#### 10.2.3 표현 형식

- **시각은 오프셋을 포함한 ISO 8601(RFC 3339)로 주고받는다.** 예: `2026-09-29T01:00:00Z`. 날짜만 있는 값은 `2026-09-29`로 쓴다(§9).
- **금액은 부동소수점으로 보내지 않는다.** 정수 최소 단위나 문자열 십진수로 보내고, 통화 코드를 함께 싣는다.
- **enum은 코드 문자열로 보낸다.** 표시 문구가 필요하면 별도 필드로 함께 준다.
- **`null`과 필드 없음의 의미를 정한다.** 응답에서 값이 없는 필드를 뺄지 `null`로 줄지 API 전체에서 하나로 정한다.
- **큰 정수 ID는 JavaScript 정밀도(2^53)를 넘을 수 있으면 문자열로 보낸다.**

#### 10.2.4 조회: 페이지네이션, 필터, 정렬, 필드 선택

- **목록은 반드시 페이지네이션한다.** 페이지 크기에 기본값과 상한을 둔다.
- **깊은 페이지나 대량 조회는 커서(키셋) 방식으로 한다.** 오프셋 방식은 작은 관리 화면에만 쓴다. 커서는 불투명한 문자열로 준다.
- **필터, 정렬, 검색은 쿼리 파라미터로 받는다.** 예: `?status=ACTIVE&sort=-createdAt`. 정렬 가능한 필드는 화이트리스트로 제한한다(§5).
- **필요하면 필드 선택(`?fields=`)을 지원한다.** 필드 선택 요구가 많아지면 GraphQL 도입 조건(§10.1)으로 검토한다.

#### 10.2.5 동시성, 캐시, 조건부 요청

- **낙관적 잠금을 HTTP로 드러낸다.** 조회 응답에 `ETag`(엔티티 버전)를 주고, 수정 요청은 `If-Match`로 받는다. 버전이 다르면 `412`를 준다(§7 `@Version`).
- **캐시 정책을 명시한다.** 조회 응답에는 `Cache-Control`을 붙인다. 개인정보나 사용자별 응답은 `private`이나 `no-store`로 둔다. 변하지 않는 리소스는 `ETag`와 `If-None-Match`로 `304`를 준다.
- **멱등 키.** 재시도될 수 있는 `POST`(생성, 결제, 발송)는 `Idempotency-Key` 헤더를 받는다. 같은 키로 다시 오면 처음 결과를 그대로 돌려준다(§2.5).

#### 10.2.6 하이퍼미디어 (Level 3)

- **링크가 실제로 쓰이는 곳에 적용한다.**
  - 페이지 이동: `next`, `prev` 링크(또는 다음 커서)를 응답에 싣는다.
  - 생성과 비동기 작업: `Location` 헤더로 새 리소스나 작업 상태 경로를 준다.
  - 상태 전이: 현재 상태에서 가능한 동작(예: 취소 가능 여부와 그 경로)을 응답에 실어, 클라이언트가 상태 규칙을 다시 구현하지 않게 한다.
- **형식은 하나로 정한다.** HAL 등 표준 형식을 고르고, 조직 응답 봉투를 쓰면 링크는 `payload` 안에 둔다.
- **모든 응답에 링크를 강제하지는 않는다.** 소비자가 쓰지 않는 링크는 계약 비용만 늘린다(YAGNI).

#### 10.2.7 버전과 변경

- **버전은 한 방식으로 정한다.** 조직 규약(URL 경로 `/v1` 등)이 있으면 따른다. 버전은 호환되지 않는 변경에만 올린다.
- **변경은 두 가지로 나눈다.**
  - 추가형(응답 필드 추가, 선택 파라미터 추가)은 기존 계약을 깨지 않으므로 바로 반영한다.
  - 파괴형(개명, 삭제, 타입·의미 변경)은 삭제 예고로 간다. 새 이름을 세우고, 옛 이름은 deprecated로 표시한 채 함께 받고, 옛 이름이 동작하는지 테스트로 지킨다. 제거 시점은 `Deprecation`, `Sunset` 헤더로 알린다. 아직 아무도 쓰지 않는 계약은 예고 없이 바로 바꾼다.
- **대외에 한 번 나간 버전은 바꾸지 않는다.** 호환되지 않는 변경은 새 버전을 병행한다.
- **enum 상수 이름과 에러 코드는 계약이다.** 문구는 바꿔도 상수 이름은 바꾸지 않는다. 받는 쪽은 모르는 enum 값이 와도 죽지 않게 한다.

#### 10.2.8 쓰기 요청

- **비운 값의 의미를 계약에 적는다.** `PUT`은 전체 교체라 빠진 필드는 지운다. `PATCH`는 보낸 필드만 바꾼다(JSON Merge Patch, RFC 7396). 경로마다 어느 쪽인지 명시하고 테스트로 고정한다.
- **검증과 문서 표기를 함께 단다.** 필수 필드는 검증 애너테이션과 스키마 required 표기를 둘 다 적고, 실제로 생성된 API 문서로 확인한다.
- **요청 본문의 모르는 필드는 무시하는 것이 기본이다.** 클라이언트가 먼저 배포돼도 깨지지 않게 하기 위해서다. 단, 소유자·권한·ID처럼 서버가 정하는 필드가 본문에 오면 조용히 무시하지 말고 `400`으로 거부한다(§5).
- **일괄 요청에는 건수 상한을 두고 부분 실패 정책을 계약에 적는다.** 전부 성공 아니면 전부 실패인지, 행별 결과를 돌려주는지 정한다.
- **오래 걸리는 작업은 `202`로 접수한다.** `Location`에 작업 상태 경로를 주고, 상태 리소스는 진행 중·완료·실패와 결과 위치를 알려 준다.

### 10.3 GraphQL

도입한 경우에 따른다(§10.1).

- **스키마를 먼저 설계한다(Schema-First).** 스키마는 클라이언트가 쓰는 업무 개념으로 짓고, DB 테이블 구조를 그대로 노출하지 않는다.
- **이름 규칙**: 타입은 PascalCase, 필드와 인자는 camelCase, enum 값은 UPPER_SNAKE_CASE로 쓴다. 뮤테이션은 동사로 시작한다(`createOrder`, `cancelOrder`).
- **nullability를 의도적으로 정한다.** 반드시 있는 값만 non-null(`!`)로 둔다. 하위 서비스 장애로 비어도 되는 필드는 nullable로 두어 부분 응답이 가능하게 한다.
- **뮤테이션은 전용 입력 타입과 결과 타입을 쓴다.** `input CreateOrderInput`을 받고, 결과 타입에 변경된 리소스와 업무 오류를 담는다. 재시도될 수 있는 뮤테이션은 멱등 키를 인자로 받는다.
- **오류를 두 종류로 나눈다.**
  - 업무 오류(검증 실패, 상태 충돌)는 결과 타입의 필드(union 또는 `errors` 필드)로 스키마에 드러낸다.
  - 시스템 오류는 GraphQL `errors`에 담고, `extensions.code`로 기계가 읽는 코드를 준다. 내부 정보는 싣지 않는다(§5).
- **N+1을 막는다.** 목록 안의 연관 필드는 DataLoader로 묶어 한 번에 조회한다. 리졸버에서 행마다 조회하거나 하위 서비스를 부르지 않는다(§7).
- **페이지네이션은 커서 연결(Relay Connection) 방식으로 한다.** `first`, `after`에 상한을 둔다.
- **쿼리 비용을 제한한다.** 깊이, 복잡도, 결과 크기, 실행 시간에 상한을 둔다. 공개 클라이언트는 사전 등록된 쿼리(persisted query)만 허용하는 것을 기본으로 한다.
- **인가는 리졸버(필드) 단위로 한다.** 게이트웨이에서 쿼리 하나를 통과시켜도 그 안의 필드마다 접근 권한을 확인한다. 식별값은 인자가 아니라 인증 컨텍스트에서 꺼낸다(§5).
- **운영에서는 인트로스펙션을 막거나 인증된 사용자로 제한한다.**
- **버전 번호를 붙이지 않는다.** 스키마는 필드 추가로 진화하고, 없앨 필드는 `@deprecated(reason: "...")`로 표시한 뒤 사용량이 0이 되면 지운다(§2.8). 필드의 타입이나 의미를 바꾸지 않고 새 필드를 만든다.
- **하위 서비스 호출에는 타임아웃을 걸고, 일부 실패는 부분 응답으로 돌려준다(§2.6).**
- **HTTP 캐시가 통하지 않는다는 점을 설계에 반영한다.** 조회를 `GET`과 persisted query로 받아 캐시하거나, 리졸버 계층에 캐시를 둔다.
- **여러 서비스의 그래프를 합쳐야 하면 페더레이션을 쓴다.** 각 서비스가 자기 타입을 소유하고, 한 서비스가 다른 서비스의 타입을 정의하지 않는다(§2.4 데이터 소유).

### 10.4 공통

- **외부 호출 클라이언트는 §2.6(타임아웃, 재시도, 서킷)과 §2.4(관대한 수신자)를 따른다.**
- **API마다 레이트 리밋을 둔다.** 넘치면 `429`와 `Retry-After`를 준다(§2.6).
- **추적 ID를 요청과 응답 헤더로 주고받는다(§2.7).**
- **계약은 자동으로 검증한다.** OpenAPI와 GraphQL 스키마의 변경은 CI에서 이전 버전과 비교해 파괴적 변경을 잡는다(§12).

## 11. 의존성

- **버전은 정확히 고정한다.** 동적 버전(`latest.release`, `1.+`)을 쓰지 않는다.
- **버전은 한 곳(BOM, version catalog)에서 관리한다.** 모듈마다 버전을 따로 적지 않는다.
- **메이저 업그레이드 뒤에는 실제로 해석된 버전을 확인한다.** 공용 라이브러리가 끌고 온 BOM이 선언한 버전을 조용히 덮을 수 있다.
- **의존성은 최소로 둔다.** 표준 라이브러리나 이미 있는 의존성으로 되는 일에 새 라이브러리를 들이지 않는다.
- **정기적으로 올린다.** 자동 갱신 도구로 작은 단위로 자주 올리고, 한꺼번에 몰아 올리지 않는다.

## 12. 테스트

- **테스트 피라미드를 따른다.** 도메인 단위 테스트가 가장 많고, 어댑터 통합 테스트가 그다음, 끝까지 가는 테스트는 핵심 흐름만 둔다.
- **도메인은 프레임워크 없이 테스트한다.** 헥사고날 구조의 이점이다.
- **통합 테스트는 운영과 같은 엔진으로 한다.** DB, 캐시, 브로커는 Testcontainers로 띄운다. 호환 모드 인메모리 DB로 대신하지 않는다.
- **서비스 사이 계약은 계약 테스트로 지킨다.** 소비자 주도 계약 테스트나 OpenAPI 스펙 검증으로, 제공자가 계약을 깨면 빌드에서 잡는다.
- **결과와 상태를 검증한다.** `times(N)` 같은 호출 횟수 검증은 내부 구현에 결합된다. 외부 의존은 목보다 동작하는 `Fake` 구현을 먼저 고른다.
- **되돌릴 수 없는 일을 하는 코드부터 테스트한다.** 외부 호출, 상태 전이, 금액·권한 판정이 여기에 해당한다.
- **결정과 계약을 테스트로 고정한다.** 호환 필드, 비운 값의 의미, 경계값, 공개 경로 목록, 아키텍처 의존 방향이 대상이다.
- **테스트 이름에 무엇을 지키는지 적는다.**
- **경계값을 넣는다.** 빈 입력, 전부 오류, 0, 상한, 상한+1, 시간대 경계(자정 전후)가 대상이다.
- **테스트는 서로 독립적이고 결정적이어야 한다.** 실행 순서, 현재 시각, 외부 네트워크에 기대지 않는다.

## 13. 주석과 문서

- **코드가 스스로 설명하게 쓴다.** 이름과 구조로 의도를 드러내고, 주석은 코드로 표현할 수 없는 것에만 쓴다.
- **주석은 짧게, 입력·출력·핵심 동작만 쓴다.** JavaDoc, 코드 주석, 설정 주석, API 문서, SQL 주석, 테스트 이름에 모두 적용한다.
  - 클래스 JavaDoc은 요약 1줄에 보조 1~2문장이면 된다.
  - `@param`, `@return`은 이름만으로 모르는 것에만 쓴다.
  - 명령조("~해라")를 쓰지 않는다.
- **넣는 것**: 코드만 봐서는 모르는 '왜' 한 줄. 함정, 호출부 책임, 의도된 비표준 같은 것이다.
- **넣지 않는 것**: 설계 경위, 날짜, 티켓 키, 논의 과정, 변경 이력. 상세한 '왜'는 `aiDoc`에(§15), 이력은 git에 둔다.
- **코드를 고치면 그 위 주석도 같이 고친다.**
- **팀이 지켜야 할 계약은 코드에 둔다.** 상수, enum, 타입, 테스트가 그 자리다.
- **API 문서는 계약만 쓴다.** 서버 내부 사정은 쓰지 않고, 소비자의 행동이 달라지는 내용만 쓴다.
  - 엔드포인트 설명은 두세 줄로 쓴다. 필드별 계약은 필드 스키마 설명에 둔다.
  - 예시 값에 실제 개인정보나 토큰을 넣지 않는다.
- **리포에 커밋하는 md는 `README.md`만 둔다.** 실행 방법과 구조 개요만 담는다. 설계 근거와 계획은 `aiDoc`에 둔다.

## 14. 검증, 보고, Git

- **빌드와 테스트를 못 돌렸으면 결론에 "미검증"이라고 적는다.** 실행할 명령을 그대로 드려 사용자에게 요청하고, 결과를 받아 이어간다.
- **추론보다 실측을 믿는다.** 근거의 신뢰도는 실데이터 > 실제 실행 결과 > 코드 > 주석·예시·픽스처 순이다. 실측하지 않은 것은 "추론"이라고 밝힌다.
- **순환 근거를 만들지 않는다.** 내가 제안한 값을 나중에 "확정된 요구사항"처럼 인용하지 않는다.
- **git 충돌이 없다고 정상인 것은 아니다.** 병합이나 체리픽 뒤에는 시그니처 변경과 중복 삽입을 확인하고, 반드시 빌드한다.
- **커밋은 작고 한 가지 목적만 담는다.** 메시지는 한국어로, 되도록 한 줄 제목만 쓴다. 조직에 접두사나 티켓 키 관례가 있으면 따른다. `Co-Authored-By` 같은 AI 작성 표기는 어떤 경우에도 넣지 않는다.
- **커밋, push, 머지는 사용자가 요청할 때만 한다.** 여러 환경으로 반영할 때는 한 단계씩 하고, 앞 단계가 머지됐는지 확인한 뒤 다음으로 간다.
- **개인 설정(에디터, 플러그인, 로컬 자격증명)이 리포에 올라가지 않게 한다.**
- **git이 추적하지 않는 파일(`aiDoc/` 등)은 지우면 복구할 수 없다.** 삭제·정리 전에 확인한다.

## 15. aiDoc — 코드 작성 근거 문서와 ADR

다음 AI(와 사람)가 "이 코드가 왜 이렇게 쓰였는지"를 상세히 알 수 있게, 코드를 작성·수정할 때마다 근거를 남긴다. 코드 주석은 짧게 두고, 상세한 내용은 여기에 쓴다.

- **위치**: `<프로젝트 루트>/aiDoc/`.
  - `aiDoc/README.md`: 문서 목록을 한 줄씩 적는다.
  - `aiDoc/adr/NNNN-<제목>.md`: 아키텍처 결정 기록(ADR). 번호는 순서대로 붙이고, 뒤집힌 결정은 지우지 않고 "대체됨: NNNN"으로 표시한다.
  - `aiDoc/<기능 또는 주제>.md`: 기능별 작성 근거. 같은 주제를 다시 고칠 때는 새 파일을 만들지 않고 기존 파일을 갱신한다.
- **커밋하지 않는다.** ADR을 포함한 `aiDoc/` 전체가 로컬 전용이다. 처음 만들 때 `.git/info/exclude`에 `aiDoc/`을 추가한다. `.gitignore`는 수정하면 그 자체가 커밋 대상이 되므로 건드리지 않는다. `git status`에 `aiDoc/`이 나오지 않는지 확인한다.
- **쓰는 시점**: 코드를 작성·수정한 그 작업 안에서 쓴다. 코드를 작성하기 전에는 관련 `aiDoc` 문서부터 읽는다.
- **ADR에 담을 내용**: 맥락(문제와 제약), 결정, 검토한 대안과 버린 이유, 결과(얻는 것과 잃는 것), 상태(제안·채택·대체됨), 날짜.
- **기능 문서에 담을 내용** (상세히):
  1. 목적: 무엇을 왜 만들었나(요구사항, 문제 상황)
  2. 결정과 근거: 적용한 원칙(이 문서의 절 번호), 참고한 코드와 조직 규약
  3. 버린 대안: 검토했다가 택하지 않은 방법과 이유(다시 제안되지 않도록)
  4. 변경 파일: 파일 경로와 각 파일에서 바꾼 것
  5. 함정과 주의: 코드만 봐서는 모르는 전제, 의도된 비표준, 건드리면 깨지는 곳
  6. 롤백 방법
  7. 검증 상태: 빌드·테스트·실측 여부와 결과, 미검증 항목
  8. 남은 일과 미결 사항
  9. 날짜(`YYYY-MM-DD`)와 변경 이력
- **사실과 추론을 구분한다.** 실측·확인한 것과 추론한 것을 나눠 적는다. 사용자가 확정한 결정은 "사용자 확정"이라고 표시한다.
- **이 문서의 원칙과 다르게 한 곳은 반드시 적는다.** 어떤 원칙을 왜 따르지 않았는지 적는다.
- **비밀 값을 적지 않는다.** 커밋되지 않더라도 자격증명, 토큰, 개인정보는 넣지 않는다.
- **기존 로컬 문서 폴더와의 관계**: 기존 리포에 로컬 전용 문서 폴더(예: gitignore된 `docs/`)가 있으면 그대로 두고 참조만 한다. 새로 쓰는 근거는 `aiDoc/`에 쓴다.

## 16. 웹 접근성 지원

**기준**: 한국형 웹 콘텐츠 접근성 지침(KWCAG 2.2)과 WCAG 2.2 AA. 화면 구현은 프론트엔드 몫이고, 백엔드는 **접근성을 구현할 수 있는 데이터, 동작, 산출물**을 책임진다. 접근성 요구는 API 계약 단계에서 프론트엔드와 함께 정한다(§1).

### 16.1 데이터 계약

- **비텍스트 콘텐츠에 대체 수단을 담을 자리를 둔다.**
  - 이미지를 다루는 리소스에는 대체 텍스트 필드(`altText`)를 둔다. 장식용 이미지인지 표시할 수 있게 한다.
  - 동영상과 음성 콘텐츠에는 자막(WebVTT 등), 원고(대본), 필요하면 수어·음성 해설 자원을 연결할 수 있게 한다. 자막 제공 여부를 조회할 수 있게 한다.
  - 차트나 통계 이미지로 보여 줄 값은 원본 수치도 API로 함께 준다.
- **언어 정보를 준다.** 콘텐츠마다 언어 코드(BCP 47, 예: `ko`, `en`)를 저장하고 응답에 실어, 화면이 `lang`을 정확히 표시할 수 있게 한다.
- **텍스트는 텍스트로 준다.** 서버에서 글자를 이미지로 만들어 보내지 않는다(문자 이미지 금지).
- **의미 있는 순서를 보장한다.** 목록, 목차, 단계 정보는 읽는 순서대로 정렬해 주고, 순서 필드를 명시한다.
- **리치 텍스트는 구조를 유지한다.** 제목, 목록, 표, 링크 같은 의미 구조를 저장·정제 과정에서 없애지 않는다(§5.2 XSS 정제는 허용 태그 목록으로 하되 구조 태그는 허용한다).
- **링크와 버튼 문구는 목적을 알 수 있게 준다.** "여기", "더보기"만 있는 문구를 API 데이터로 내려보내지 않는다.

### 16.2 오류와 안내

- **오류는 사용자가 고칠 수 있게 구체적으로 준다.** 어느 입력 칸이 왜 틀렸는지, 어떤 형식이어야 하는지를 필드 단위로 준다(§10.2.2). 내부 원인은 숨긴다(§5.5). 로그인·계정 찾기처럼 구체적인 안내가 공격 정보가 되는 곳은 보안을 우선한다(§0 순서).
- **메시지는 다국어를 지원한다.** 기계가 읽는 코드와 사람이 읽는 문구를 나누고, 문구는 사용자 언어로 준다.
- **색이나 모양만으로 의미를 전달하는 값을 보내지 않는다.** 상태는 코드와 문구로 준다.

### 16.3 시간 제한과 인증

- **시간 제한은 조절할 수 있게 한다.** 세션, 입력 제한 시간, 인증 번호 유효 시간에는 남은 시간 조회와 연장 요청 API를 둔다. 연장 상한은 보안 정책이 정한다(§5.3). 만료 전에 안내할 수 있게 만료 시각을 응답에 준다.
- **시간이 만료돼도 입력한 내용을 잃지 않게 한다.** 긴 입력 양식은 임시 저장을 지원한다.
- **인지 기능 시험에만 의존하는 인증을 두지 않는다(WCAG 2.2 접근 가능한 인증).** 문자 CAPTCHA만으로 막지 않고, 비밀번호 관리자와 붙여 넣기를 막지 않으며, 대체 인증 수단을 둔다.
- **같은 정보를 다시 입력하게 하지 않는다.** 한 흐름 안에서 이미 받은 정보는 서버가 이어 받는다.

### 16.4 서버가 만드는 산출물

- **HTML 이메일**: `lang` 속성, 이미지 대체 텍스트, 의미가 드러나는 제목 구조, 충분한 대비를 갖춘다. 레이아웃 표에는 `role="presentation"`을 붙이고, 이미지만으로 된 메일을 보내지 않는다. 텍스트 대안 본문(`text/plain`)을 함께 보낸다.
- **다운로드 문서(엑셀, PDF)**
  - 엑셀은 첫 행에 머리글을 두고, 병합 셀과 빈 행으로 구조를 표현하지 않고, 시트 이름을 의미 있게 짓는다.
  - PDF는 태그가 있는 PDF로 만들고 문서 언어와 제목을 설정한다.
- **서버 렌더링 HTML**: 시맨틱 마크업, 제목 계층, 폼 레이블, 페이지 제목, `lang`을 갖춘다.

### 16.5 검증

- 접근성 관련 필드(대체 텍스트, 자막, 언어)가 비어 있는 데이터를 조회할 수 있게 하여 운영 중 누락을 점검할 수 있게 한다.
- 서버가 만드는 HTML(이메일, 서버 렌더링 화면)은 자동 접근성 검사 도구로 확인한다.

## 17. 웹 호환성 지원

**기준**: 국내 「웹 호환성 준수 지침」과 웹 표준(HTTP, HTML, 유니코드 관련 IETF·W3C·WHATWG 표준). 목표는 특정 브라우저, 운영체제, 기기, 플러그인에 관계없이 같은 서비스를 받게 하는 것이다. 백엔드는 **표준을 따르는 응답과 브라우저에 기대지 않는 동작**을 책임진다.

### 17.1 표준 HTTP

- **HTTP 표준(RFC 9110)대로 동작한다.** 메서드, 상태 코드, 헤더를 표준 의미로 쓴다(§10.2.2). 특정 브라우저의 비표준 동작에 기대지 않는다.
- **`Content-Type`을 정확히 준다.** 문자 응답에는 `charset=UTF-8`을 붙인다. 브라우저가 형식을 추측하지 않게 `X-Content-Type-Options: nosniff`를 함께 보낸다(§5.3).
- **콘텐츠 협상을 표준 헤더로 한다.** 압축은 `Accept-Encoding`(gzip, br), 언어는 `Accept-Language`로 받고 `Vary`를 정확히 붙인다.
- **User-Agent로 기능을 가르지 않는다.** 브라우저 종류에 따라 다른 응답이나 기능을 주지 않는다. 불가피한 호환 우회는 기능 단위로 하고 ADR로 남긴다.
- **특정 플러그인이나 설치 프로그램을 요구하지 않는다.** ActiveX, 실행 파일 설치, 브라우저 확장에 기대는 인증·보안·결제 흐름을 만들지 않는다.

### 17.2 문자 인코딩

- **입력, 저장, 출력 전 구간을 UTF-8로 통일한다.** DB는 `utf8mb4`를 쓴다(한글과 이모지). 다른 인코딩을 쓰는 외부 시스템과는 경계 어댑터에서 변환한다(§2.2 ACL).
- **URL의 한글과 특수 문자는 퍼센트 인코딩(RFC 3986)으로 주고받는다.**
- **유니코드 정규화를 정한다.** 검색과 중복 비교에 쓰는 문자열은 NFC로 정규화해 저장한다(맥에서 올린 한글 파일명의 자모 분리 문제 등).

### 17.3 파일 다운로드와 업로드

- **파일 다운로드는 표준 헤더로 준다.** `Content-Disposition: attachment; filename="<ASCII 대체 이름>"; filename*=UTF-8''<퍼센트 인코딩 이름>`(RFC 6266, RFC 5987) 형식으로 보내, 한글 파일명이 모든 브라우저에서 깨지지 않게 한다. 브라우저별 인코딩 분기를 만들지 않는다.
- **`Content-Type`과 `Content-Length`를 정확히 준다.** 큰 파일은 `Accept-Ranges`로 이어 받기를 지원한다.
- **업로드는 표준 `multipart/form-data`로 받는다.** 파일명 인코딩 차이를 서버에서 흡수하고, 저장 파일명은 서버가 새로 짓는다(§5.2).
- **문서 형식은 표준 형식을 쓴다.** 엑셀은 `.xlsx`(OOXML), 문서는 PDF를 기본으로 하고, 특정 프로그램에서만 열리는 형식을 기본 산출물로 삼지 않는다.

### 17.4 미디어와 콘텐츠

- **이미지와 동영상은 널리 지원되는 형식을 기본으로 준다.** 이미지는 JPEG, PNG를 기본으로 하고 WebP·AVIF는 협상이나 대체 경로와 함께 준다. 동영상은 H.264/AAC(MP4)와 HLS를 기본으로 한다.
- **반응형 이미지에 쓸 수 있게 여러 크기의 파생본이나 크기 지정 URL을 제공한다.**

### 17.5 브라우저 정책 변화 대응

- **쿠키는 최신 브라우저 정책을 전제로 만든다.** `SameSite` 기본값(Lax), 서드파티 쿠키 차단, `Secure` 요구를 전제로 인증 흐름을 설계하고, 서드파티 쿠키에 기대지 않는다.
- **CORS는 표준 사전 요청(preflight)을 정확히 처리한다.** `OPTIONS` 응답에 허용 메서드, 헤더, 노출 헤더(`Access-Control-Expose-Headers`)를 명시한다(§5.3).
- **혼합 콘텐츠를 만들지 않는다.** 응답에 싣는 모든 URL은 `https`다.
- **TLS 1.2 이상과 HTTP/2를 지원한다.** 오래된 프로토콜을 위해 보안을 낮추지 않는다.

### 17.6 시간과 숫자 표현

- **시각, 숫자, 통화는 형식화하지 않은 표준 값으로 준다.** 시각은 RFC 3339, 숫자는 JSON 숫자, 금액은 §10.2.3 규칙을 따른다. 지역별 표시 형식(날짜 표기, 천 단위 구분)은 클라이언트가 사용자 로캘로 만든다. 서버가 표시용 문자열을 줘야 하면 로캘을 명시해 만든다.

### 17.7 서버가 만드는 HTML 이메일

- **메일 클라이언트 호환을 전제로 만든다.** 인라인 스타일, 표 기반 레이아웃, 웹폰트 대체 글꼴을 쓰고, 스크립트와 외부 CSS에 기대지 않는다. 주요 메일 클라이언트(웹메일, 모바일, 데스크톱)에서 렌더링을 확인한다.

## 18. 규칙을 지키는 방법

규칙은 사람이 기억하는 것보다 도구와 순서로 지키는 편이 확실하다.

### 18.1 작업 순서

1. **읽기**: `aiDoc/`, 관련 코드, 결정 주석과 테스트를 먼저 읽는다. 유지보수인지 신규 개발인지 정한다(§0).
2. **정하기**: 용어, 경계, 계약(OpenAPI·스키마)을 먼저 정한다. 규칙과 다르게 갈 곳이 있으면 ADR부터 쓴다.
3. **테스트 먼저**: 지킬 동작(경계값, 권한, 비운 값의 의미)을 테스트로 먼저 적는다.
4. **구현**: 도메인 → 애플리케이션 → 어댑터 순서로 안쪽부터 만든다.
5. **확인**: 아래 18.3 점검표를 돈다. 빌드와 테스트를 돌린다. 못 돌렸으면 "미검증"이라고 적는다.
6. **기록**: `aiDoc` 기능 문서를 쓰거나 갱신한다.

### 18.2 도구로 강제하기

| 지킬 것 | 도구 예 | 언제 |
|---|---|---|
| 의존 방향, 계층 규칙 (§3) | ArchUnit 테스트 | 빌드 |
| 코드 형식, 스타일 (§4) | Spotless, Checkstyle | 커밋 전, 빌드 |
| 흔한 버그, 보안 약점 (§5) | SpotBugs + FindSecBugs, SonarQube | 빌드, PR |
| 의존성 취약점 (§5.9) | OWASP Dependency-Check, Dependabot/Renovate | 빌드, 매일 |
| 비밀 값 커밋 (§5.3) | gitleaks 같은 비밀 탐지 | 커밋 전, PR |
| API 파괴적 변경 (§10) | OpenAPI diff, GraphQL 스키마 검사 | PR |
| 스키마 변경 (§8) | Flyway/Liquibase 검증, 운영 `ddl-auto: validate` | 빌드, 기동 |
| 운영과 같은 DB 테스트 (§12) | Testcontainers | 빌드 |
| 접근성 (§16) | 서버 HTML 자동 검사(axe 등) | PR |

도구를 아직 못 붙였으면 해당 규칙을 18.3 점검표로 손으로 확인한다.

### 18.3 완료 전 점검표

한 줄씩 "예"가 되어야 끝난다. 해당 없는 줄은 건너뛴다.

**설계**
- [ ] 도메인 코드가 Spring, HTTP, SQL을 모르는가
- [ ] 새 규칙, 기본값이 한 곳에만 있는가
- [ ] 다른 서비스 테이블을 직접 읽거나 쓰지 않는가

**보안**
- [ ] 사용자·테넌트·소유자 ID를 요청이 아니라 인증 컨텍스트에서 꺼내는가
- [ ] 관리자가 아닌 계정으로 남의 자원에 접근해 봤는가(`404`가 나와야 한다)
- [ ] 로그와 응답에 비밀, 개인정보, 내부 원인이 없는가
- [ ] SQL, 경로, URL, 파일에 외부 입력이 검증 없이 들어가지 않는가

**데이터**
- [ ] 트랜잭션 안에 외부 호출이 없는가
- [ ] 목록 조회에 N+1과 페이지 상한 누락이 없는가
- [ ] 시각을 UTC로 저장하고, 날짜 경계를 업무 시간대로 계산했는가
- [ ] 스키마 변경이 마이그레이션 파일로 있고, 파괴적 변경을 나눴는가

**API**
- [ ] 상태 코드가 의미에 맞는가(실패를 `200`에 담지 않았는가)
- [ ] 기존 계약을 깨지 않았는가(깼다면 삭제 예고를 했는가)
- [ ] 쓰기 API가 멱등한가, 재시도될 `POST`에 멱등 키가 있는가
- [ ] 외부 호출에 타임아웃이 있는가

**마무리**
- [ ] 테스트가 결과와 상태를 검증하고, 경계값을 넣었는가
- [ ] 주석이 짧고, 상세 근거는 `aiDoc`에 있는가
- [ ] `git status`에 `aiDoc/`과 비밀 파일이 보이지 않는가
- [ ] 커밋 메시지에 AI 작성 표기가 없는가

### 18.4 규칙을 어겨야 할 때

1. 어떤 규칙을 왜 못 지키는지 적는다.
2. 대안과 그 대가를 적는다.
3. ADR(`aiDoc/adr/`)로 남긴다. 코드에는 ADR 번호를 적지 않고(§13, `aiDoc`은 커밋되지 않는다), 규칙과 다른 '왜'를 주석 한 줄로 남긴다.
4. 사용자에게 알리고 확인받는다.

규칙이 현실에 맞지 않으면 이 문서를 고치자고 제안한다. 조용히 어기지 않는다.

# 외화 적립 알림 설계 (USD·JPY, 2026-11-13)

- 요청: 데브 "외화 투자 및 알림 자동화 계획서 v1.0"(2026-11-13, 12-01 시행)과 VALUNIVO 계획 4-6. 등록·설계 입력은 VALUNIVO 864, 이 설계의 단위 기록은 VALUNIVO 867, 판단은 결정 D-28
- 배치: autoStock 안의 별도 모듈 `com.autostock.fx`(VALUNIVO D349). 거래·전략·리스크·주문 코드와 패키지·DB 테이블을 나눈다
- 상태: 설계안. 개발(4-6/dev)·운영 반영(4-6/release) 전이다. 이 문서는 규칙의 원본이고, 개발 때 코드가 이 문서와 다르면 문서를 먼저 고친다

## 2. 한 달 흐름

1. **월초(1일 09:10, AI 제안):** "이번 달 예약을 신청했으면 입력해 주세요" 안내와 아직 열린 예약 목록을 보낸다. 데브가 은행 앱에서 1개월 목표환율 예약을 하고 `/autostock_fx_reserve`로 입력한다.
2. **1일~검토 시작일 전:** 환율을 감시하지만 직접매수 검토 알림은 보내지 않는다. 데브가 체결을 확인하면 `/autostock_fx_fill`로 입력한다.
3. **검토 시작일(15일)~말일:** 6장 조건이 맞으면 통화별로 직접매수 검토 알림을 보낸다. 데브가 은행 앱에서 실제 환율을 보고 산 경우 `/autostock_fx_buy`로 입력한다. 예약은 그대로 둔다.
4. **말일 18:10:** 월말 정산 알림(7장).

## 3. 공개 환율 출처와 감시 주기

- 출처는 한국은행 ECOS `731Y001`(주요국 통화의 대원화 환율, 일별)이다. autoStock은 이미 같은 키로 원/달러(`0000001`)를 받는다(`EcosClient`). 새 키가 필요 없다(데브 몫 ③ 없음).
- 엔화 항목코드는 `0000002`("원/일본엔(100엔)", 일별)다. 실측 2026-11-13: ECOS 공개 시험 키로 `StatisticItemList` 조회(VALUNIVO 869). 상수는 `FxCurrency`에 출처 주석과 함께 둔다.
- 그날 값은 같은 날 08:30 운영 수집에는 없었고(전날 값) 15:31 조회에는 있었다(11-13, 두 통화). 정확한 게시 시각은 운영 판정 로그(`외화 검토 판정 … 관측일`)로 이어서 본다.
- 단위는 은행 앱 표시와 같게 원/1달러, 원/100엔으로 입력·계산한다.
- ECOS는 하루에 한 값이다. 운영 로그(11-13 00:06·02:45·08:30 수집 값이 모두 같음)로 보면 아침에는 전 영업일 값이다. 그날 값이 몇 시에 올라오는지는 확인 필요다. 그래서 **평일 09~18시 매시 10분**에 두 통화의 최신 관측을 받아, 마지막으로 판정한 관측일보다 새 관측일일 때만 판정한다. 하루 호출은 통화당 10번 안쪽이다.
- 실시간 환율은 아니다. 알림은 "검토해 볼 때"를 알리는 신호이고, 데브는 사기 전에 은행 앱의 실제 환율을 본다. 알림 문구에 이 점을 적는다.

## 4. 공개 환율과 은행 매수 환율의 차이 보정 (F-3)

- 예약을 입력할 때 데브는 **신청할 때 은행 앱에 보인 살 때 환율**(신청 당시 환율)을 함께 넣는다. 앱은 그 시각의 ECOS 최신 관측값과 관측일을 저장한다.
- 차이 = 신청 당시 환율 − 입력 시점 ECOS 최신값. 예약마다 따로 저장한다.
- 추정 매수 환율 = 판정 시점 ECOS 최신값 + 그 예약의 차이.
- 한계: 입력 시점의 ECOS 값은 전 영업일 값일 수 있어 그날 움직임이 차이에 섞인다. 은행 우대율이 바뀌면 어긋난다. 그래서 알림은 검토 신호로만 쓰고(3장), 정산에서 실제 체결 환율과 추정 환율의 차이를 보여 다음 달 판단에 쓰게 한다.

## 5. 예산과 이월 예약 (F-1)

- 달은 KST 달력월이다.
- **노출액** = 이번 달에 체결로 입력된 금액(예약 체결 + 직접매수) + 아직 체결·취소되지 않은 모든 예약의 금액(신청한 달과 무관).
- 직접매수 검토 알림은 `노출액 + 그 통화 직접매수 금액 ≤ 월 상한`일 때만 보낸다.
- 예약 입력 때 `노출액 + 새 예약 금액 > 월 상한`이면 저장은 하고 경고를 함께 답한다(은행 예약은 이미 했으므로 기록을 거절하지 않는다).
- 정산 표시는 실제 돈이 나간 때를 따라 체결한 달로 센다. 판단(노출액)은 아직 열린 예약을 모두 넣어 보수적으로 막으므로, 지난달 예약이 이번 달에 체결돼도 상한을 넘는 직접매수 알림이 나가지 않는다.
- 확인 필요: 은행 목표환율 예약이 신청 때 원화를 묶어 두는지 체결 때 빼는지. 어느 쪽이어도 노출액 방식은 보수적이라 설계를 바꾸지 않는다.

## 6. 직접매수 검토 알림 조건 (F-2·F-4·F-5)

통화마다 **기준 예약**은 그 통화의 열린 예약 가운데 가장 최근에 신청한 것이다. 아래가 모두 맞을 때 보낸다.

| 번호 | 조건 |
|---|---|
| C1 | 오늘(KST)의 일 ≥ `review-start-day`(15) |
| C2 | 기준 예약이 있고 체결 입력이 없다 |
| C3 | 이번 달 그 통화의 직접매수 입력이 없다(통화당 한 달 1회) |
| C4 | 추정 매수 환율 ≤ 기준선. 기준선 = (신청 당시 환율 + 예약 환율) ÷ 2. 비교는 반올림 없이 하고 표시만 소수 둘째 자리 |
| C5 | 5장 예산 조건 |
| C6 | 중복 아님: 그 기준 예약에 대해 앞 판정에서 C4가 거짓이었다가 이번에 참이 됐을 때(처음 판정이 참이면 그때 한 번), 그리고 그 통화로 오늘 보낸 검토 알림이 없을 때 |

- 예약 입력 때 `예약 환율 ≥ 신청 당시 환율`이면 거절한다. 그러면 기준선 < 신청 당시 환율이라 "신청 당시보다 하락"은 C4에 들어간다(F-2).
- C6은 같은 조건이 이어진다는 이유만으로 날마다 반복하지 않기 위해서다(VALUNIVO 디자인 기초지식 5부). 환율이 기준선 위로 올라갔다가 다시 내려오면 다시 보낸다.
- C6의 "앞 판정이 아래였는가"(`last_review_below`)는 C1·C2·C3·C5가 맞는 검토 대상일 때만 갱신하고, 대상이 아니면 비운다. 15일 전부터 아래였다는 이유로 15일 첫 알림이 막히지 않게 하기 위해서다. 새로 내려왔지만 그 통화로 오늘 이미 보냈으면 상태를 바꾸지 않아 다음 판정에서 다시 본다. 공개 환율이나 차이가 없으면 판정하지 않고 상태를 유지한다(VALUNIVO 868, `FxReviewRule`).

## 7. 체결·만료·월말 정산 (F-6)

- 앱은 체결을 알 수 없다. 데브가 `/autostock_fx_fill`로 넣는다. 직접매수 검토 알림 끝에 "예약이 체결됐으면 입력" 안내를 붙인다.
- 만료일(기본 신청일 + 1개월)이 지나도 자동으로 닫지 않는다. 노출액에 남겨 두고 정산에서 묻는다(체결 여부를 모르는 채로 예산에서 빼지 않는다).
- **월말 정산 알림(말일 18:10):** 통화별 이번 달 체결(예약·직접) 원화 합계·외화 합계·가중 평균 환율, 노출액과 상한, 추정 환율과 실제 체결 환율의 차이, 만료일이 지난 미입력 예약 번호(체결이면 `fx_fill`, 아니면 `fx_cancel`을 쓰라는 안내). 이번 달 직접매수가 없으면 그 사실만 적는다.

## 8. 데이터 (마이그레이션은 개발 때 모든 브랜치 최대 번호 다음)

| 테이블 | 열 |
|---|---|
| `fx_reservation` | id, currency(`USD`·`JPY`), requested_on, request_rate, reserve_rate, amount_krw, ref_rate(입력 때 ECOS), ref_observed_on, spread, expires_on, status(`OPEN`·`FILLED`·`CANCELLED`), filled_on, filled_rate, last_review_below(C6용), created_at, updated_at |
| `fx_direct_buy` | id, currency, bought_on, rate, amount_krw, status(`DONE`·`CANCELLED`), created_at |
| `fx_alert_log` | id, kind(`REVIEW`·`MONTH_START`·`MONTH_END`), currency, reservation_id, observed_on, sent_at. (kind, currency, reservation_id, observed_on) 유일 |

- 환율은 `numeric(12,4)`, 원화는 정수. 계산은 `BigDecimal`.
- 판정 규칙은 프레임워크·DB를 모르는 순수 클래스(`FxReviewRule`)에 두고, 일정·DB·텔레그램은 바깥 층에 둔다(VALUNIVO K-23).
- 알림 기록과 발송 순서는 기존 공모주 알림 기록(`ipo_alert_log`)과 같은 방식으로 한다. 기록의 유일 키가 중복 발송을 막는다(BE BC-17).

## 9. 입력 명령 (설명서 `commands`에 더함, 계약 1.1 유지)

| id | 위험 | 인수 | 하는 일 |
|---|---|---|---|
| `fx_view` | query | 없음 | 이번 달 요약(노출액·상한·통화별 체결)과 열린 예약 목록 |
| `fx_reserve` | change | currency, reserve_rate, amount, request_rate, expires(선택) | 예약 기록. 4장 차이 계산, 5장 경고, 6장 입력 거절 |
| `fx_fill` | change | no, rate(선택, 기본 예약 환율), date(선택, 기본 오늘) | 예약 체결 기록 |
| `fx_buy` | change | currency, rate, amount, date(선택) | 직접매수 기록 |
| `fx_cancel` | l1_ceiling | no(`R12`·`B3` 형식) | 잘못 넣은 기록이나 은행에서 취소한 예약을 취소 상태로(지우지 않음) |

- 앱 직접 이름은 `/autostock_fx_reserve`처럼 된다(32자 이내). 니보 경로는 플랫폼 카탈로그가 같은 원천에서 만든다.
- `fx_cancel`은 기록을 고치는 성격이라 사다리 천장 L1로 둔다(VALUNIVO K-03의 삭제 취지). 나머지 입력은 기록만 하고 돈을 움직이지 않으므로 `change`다.
- 설명서 `app_version`을 올린다. 원천과 실행 집합이 같은지는 기존 시험이 단정한다.

## 10. 알림 문구 (예시 값은 합성)

```text
[외화 검토] USD 직접매수 검토 조건에 닿았습니다
추정 살 때 환율 1,341.20 (공개 1,326.70 + 예약 때 차이 14.50, 11-27 기준)
기준선 1,345.00 = (신청 당시 1,360.00 + 예약 1,330.00) ÷ 2
예약 R12 미체결 · 이번 달 노출 100,000 / 상한 130,000원 · 직접매수 20,000원 가능
사기 전에 은행 앱의 실제 환율을 확인해 주세요. 샀으면 /autostock_fx_buy, 예약이 체결됐으면 /autostock_fx_fill R12
```

- 한 통은 수백 자라 텔레그램 4,096자 한도(BE BC-40) 안이다. `fx_view`는 열린 예약을 최대 10건만 보이고 나머지는 개수로 적는다.
- 발송 주체 표시와 플랫폼 사본은 기존 autoStock 알림 경로를 그대로 쓴다(VALUNIVO K-07).

## 11. 설정 (`application.yml`의 `fx.accumulation`)

| 키 | 기본 | 뜻 |
|---|---|---|
| `alerts-enabled` | `false` | 감시·월초·월말 알림. 운영 반영 뒤 12-01 전에 켠다. 입력 명령은 꺼도 동작 |
| `monthly-cap-krw` | `130000` | 월 상한 |
| `direct-buy-usd-krw`·`direct-buy-jpy-krw` | `20000` | 통화별 직접매수 금액 |
| `review-start-day` | `15` | 검토 시작일(포함, 1~28) |

감시 시간(평일 09~18시 매시 10분, KST)은 설정이 아니라 `FxReviewScheduler`의 일정 식으로 고정했다(VALUNIVO 869).

## 12. 개발 단계 시험 계획 (4-6/dev)

| 대상 | 시험 |
|---|---|
| `FxReviewRule` | C1 경계(14일·15일), C4 같음 경계, C5 같음 경계, C6 거짓→참·참 연속·하루 2회, 엔화 단위, 예약 환율 ≥ 신청 당시 거절 |
| 노출액 | 지난달 열린 예약 포함, 취소 제외, 체결 달 귀속 |
| DB | 새 마이그레이션·저장소의 DB 통합 시험(autoStock 관문 필수, D336), 유일 키로 중복 알림이 막히는지 |
| 조립 경로 | 일정 → ECOS(가짜 응답) → 판정 → 기록 → 발송 대역까지 한 번(VALUNIVO RM-54) |
| 명령 | 설명서 원천과 실행 집합 일치(기존 시험), 다섯 명령의 인수 오류 답 |
| 실측 | 개발 키로 엔화 항목코드 확인, 며칠간 관측일과 수집 시각을 기록해 게시 시각 확인(3장) |

## 13. 확인 필요와 한계

- 그날 값의 정확한 게시 시각(3장, 08:30~15:31 사이까지 확인). 엔화 항목코드는 869에서 확인을 마쳤다.
- 은행 예약의 원화 출금 시점(5장, 설계에는 영향 없음).
- 추정 매수 환율은 근사다(4장). 실제 매수 판단은 데브가 은행 앱에서 한다.
- 운영 반영은 12-15 전이 목표다(15일 검토 시작). autoStock 운영 변경 시간 창(평일 16:00~다음 날 08:00·주말)을 지킨다.

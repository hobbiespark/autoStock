## 5. 권고 — 용도로 나눈다

- **운영 데이터(앱이 쓰고, 다시 구할 수 없는 것) → DB.**
  - 주문·이벤트·리스크·성과·공시·휴장일은 이미 DB에 있다.
  - **분봉도 DB로 옮기기를 권한다.** 예: `minute_bars`, 기본키(종목, 시각). 규모는 5종목 × 연 약 9.6만 행 = 연 약 48만 행으로 PostgreSQL에 부담이 없다.
  - 그러면 백업·복원 리허설에 자동으로 포함되고, 중복 없는 업서트와 놓친 날 따라잡기가 쉬워진다.
  - 연구용은 CSV로 내보낸다.
- **연구·백테스트 스냅샷(고정된 과거 자료) → 파일 유지.**
  - 이유: 판정을 재현하려면 자료가 고정돼야 하고, 수집·분석 스크립트가 Python이다.
  - 대신 매니페스트(출처, 받은 날, 행 수, sha256)를 두고, 압축본을 D 드라이브 밖에 오프사이트 백업한다.
- **증빙(`docs/measured`) → git 유지.**
- **비밀값 → 파일·환경변수 유지.** DB와 git에는 두지 않는다.
- **`aiDoc/market-data` → 리포에서 제거(`git rm`).**
  - 이미 공개된 이력까지 지우려면 히스토리를 다시 쓰고 강제 푸시해야 한다. 이건 별도로 정한다.

## 7. DB로 옮길 때의 형태 — PostgreSQL 16 실측 (2026-10-01)

> **2026-10-01 사용자 결정으로 TimescaleDB 하이퍼테이블을 쓴다.** 아래 "파티션, BRIN, TimescaleDB는 쓰지 않는다"는 판단은 바뀌었다. 이 절의 수치는 일반 테이블 기준선으로 남긴다. 하이퍼테이블 실측(같은 10년 498만 행: 81MB, 연속 집계 일봉 9ms)은 `data-platform-postgres.md` 6.3절.

### 실측 조건
- 컨테이너 PostgreSQL 16.13(운영과 같은 16 계열 — 저장 형식이 같다)에 합성 분봉 **498만 행**을 넣었다. 10년 × 평일 × 382분 × 5종목이고, 가격대는 실제 5종목 수준이다.
- 숫자는 이 환경 기준이다. 덤프 크기는 실데이터 엔트로피에 따라 더 커질 수 있다.

### 형태별 결과

| 형태 | 표 | 기본키 인덱스 | 합계 | 행당 |
|---|---|---|---|---|
| A. 기존 관례: 가격 `NUMERIC(19,4)`, 종목 `VARCHAR(16)` | 440MB | 206MB | 646MB | 136B |
| B. 최적화: 가격 `INTEGER`(원), 8→4바이트→가변 순 배치, 종목 `VARCHAR(6)` | 364MB | 206MB | 570MB | 120B |
| C. B + 운영과 같은 적재 순서(하루 단위, 종목별 시간순) | 364MB | **150MB** | **514MB** | 103B |
| D. C인데 기본키를 (시각, 종목) 순으로 | 364MB | 205MB | 569MB | — |

### 조회·적재 실측(C)
- 종목 1개·하루(382행): **2ms**
- 종목 1개·1년(99,702행) 집계: **25ms**. D는 31ms.
- 하루치 5종목 1,910행 적재: **7ms**
- 같은 날 다시 적재: **0행 추가, 9ms**(중복 없이 몇 번이고 다시 돌릴 수 있다)
- 10년치 덤프(`pg_dump -Fc`): **55MB, 10초**. 합성 데이터라 실데이터는 더 클 수 있다.

### 실데이터 검증
- PC `data/minutes` 2,674행(9/23·10/1)에서 아래 CHECK 후보 위반은 0건이었다.
- 위반 후보로 본 것: 저가 0 이하, 고가<저가, 저가>시가·종가, 고가<시가·종가, 거래량 음수·0, 누적<분거래량.

### 권하는 정의

```sql
CREATE TABLE minute_bars (
    bar_time   TIMESTAMPTZ NOT NULL,   -- 분 시작 시각. 기존 관례(Instant ↔ TIMESTAMPTZ, aiDoc/time.md)
    volume     BIGINT      NOT NULL,
    acc_volume BIGINT      NOT NULL,   -- API 원본 보존(파생 가능 — 빼면 행당 8B 절약)
    open       INTEGER     NOT NULL,   -- 원 단위 정수(KRX 호가에 소수 없음). 주문 계산은 읽을 때 Price로 바꾼다
    high       INTEGER     NOT NULL,
    low        INTEGER     NOT NULL,
    close      INTEGER     NOT NULL,
    symbol     VARCHAR(6)  NOT NULL,
    PRIMARY KEY (symbol, bar_time),    -- 유일한 인덱스. 종목·기간 조회와 중복 방지를 함께 맡는다
    CHECK (volume >= 0 AND acc_volume >= volume),
    -- 체결 없는 분(거래정지·VI 등)이 0으로 와도 잃지 않게, 거래량이 있을 때만 시고저종 일관성을 본다
    CHECK (volume = 0 OR (low > 0 AND low <= LEAST(open, close) AND high >= GREATEST(open, close)))
);
```

### 결정과 근거
- **(종목, 시각) 기본키, 대리키 없음.**
  - 운영 적재 순서(종목별 시간순)에서 인덱스가 촘촘하다(150MB vs 205MB).
  - 종목·기간 조회가 그대로 인덱스 범위 스캔이 된다.
- **가격 `INTEGER`.**
  - 기존 `NUMERIC(19,4)` 관례와는 다르다. 그래도 원 단위 원시 시세라 정수가 정확하고, 표가 17% 작고 정수 연산이라 빠르다.
  - 관례를 따르는 것도 가능한 선택이다(10년 +76MB).
- **컬럼 순서는 8바이트 → 4바이트 → 가변.** 정렬 패딩을 줄인다.
  - 종목을 `SMALLINT` 번호로 바꾸는 것도 검토했지만, 정렬 단위(8B) 때문에 표·인덱스 크기가 줄지 않아 버렸다(계산).
- **적재는 JPA가 아니라 `JdbcTemplate` 한 문장으로.**
  - 종목·페이지 단위로 `INSERT … SELECT FROM unnest(배열들) ON CONFLICT (symbol, bar_time) DO NOTHING`을 쓴다.
  - 왕복 1회이고, 추가된 행 수가 정확히 나오며, 다시 돌려도 안전하다.
  - 1년치 되채우기(종목당 약 9.6만 행)도 같은 문장을 900행 페이지마다 쓰면 된다.
- **파티션, BRIN, TimescaleDB는 쓰지 않는다.** → 2026-10-01 사용자 결정으로 바뀜(이 절 첫 안내)
  - 10년치가 5백만 행·0.5GB라 일반 B-tree로 충분하다.
  - TimescaleDB는 도커 이미지까지 바꿔야 한다.
- **다시 볼 기준:** 유니버스 전체(약 2,700종목) 분봉을 쌓으면 연 2.5억 행이 된다. 그때는 월 단위 파티션 + BRIN, 또는 TimescaleDB 압축을 검토한다.
- **유지보수:** 추가만 하는 표라 PostgreSQL 13+의 삽입 기준 autovacuum으로 충분하다. 튜닝은 필요 없다.

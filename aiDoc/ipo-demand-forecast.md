## 1. 목적

- **지표 자동 입력:** 공모주 권고 필터(ADR-9 ②)는 기관경쟁률과 의무보유확약비율 두 지표로 판정한다.
  - 지금까지는 둘 다 수동 입력(`POST /api/ipo/{id}/metrics`)으로만 채울 수 있었다.
  - 그래서 대부분의 딜이 PENDING(판정 보류)으로 남았다.
- **함께 고친 결함:** 상장사 유상증자가 공모주 딜로 들어와 공모주 화면과 청약 알림에 나왔다.
  - 예: 삼성바이오로직스·뷰노·한울반도체 등. 발행공시 목록의 "증권신고서(지분증권)"에 공모주와 유상증자가 섞여 있기 때문이다.

## 3. 결정과 구현

### 지표 정의
- **기관경쟁률:** (가) 표 "경쟁률" 행의 "합계" 열이다. 기관 배정 주식수 대비 신청 수량의 단순경쟁률로, 언론의 "기관 경쟁률 N대 1"과 같다.
- **의무보유확약비율(수량 기준):** (다) 표 "합계" 열의 "수량"으로 계산한다.
  - 계산: 확약 행(기간별)의 합 ÷ 합계 행. 0~1로 저장한다(소수 넷째 자리, 예: 0.2175).
  - 화면과 권고 사유에는 21.75%처럼 보인다.
  - "합계" 열이 없으면 모든 표의 "수량" 열을 더한다.
- **검산:** 둘 중 하나라도 어긋나면 확약비율을 비워 둔다. 경쟁률은 따로 남는다.
  - ① 확약 합 + 미확약 = 합계
  - ② 확약 표 합계 = 참여 내역 표 합계
  - 틀린 지표로 권고하는 것보다 비워 두고 수동 입력을 기다리는 편이 낫다.

### 수집 흐름(평일 08:20 배치와 따라잡기, `IpoSyncScheduler`)
1. 최근 14일 발행공시 목록에서 증권신고서(지분증권)를 받는다(기존).
2. 공시마다 주요정보를 조회하고 공모 종류를 판정한다.
   - 유상증자면 새 딜을 만들지 않는다.
   - 이미 있던 딜이면 판정만 남긴다.
3. 판정 전 옛 딜을 배치마다 최대 10개 회사씩 판정한다(`IpoOfferingClassifier`).
4. 수요예측 지표를 채운다(`IpoDemandForecastCollector`).
   - 대상: 공모주이고 지표가 아직 없는 딜. 청약 시작이 45일 이내로 지났거나 아직 오지 않았어야 한다. 일정을 모르면 접수 45일 이내.
   - 회사별 발행공시 목록에서 [발행조건확정]을 찾아 최신부터 최대 3건 원본을 읽는다.
     - 표가 없는 건은 건너뛴다.
   - 같은 회사의 딜(정정 신고서마다 한 행)에 같은 값을 넣는다.
   - 한 배치에 최대 10개 회사.
5. 상태와 권고를 다시 계산하고 청약 D-1·당일 알림을 낸다(기존). 유상증자 딜은 권고·알림에서 뺀다.

### 수동 입력과의 관계
- 화면이나 API로 넣은 지표는 출처가 `MANUAL`이 되고, 자동 입력이 덮지 않는다.
- V11 이전에 들어간 지표는 수동 입력 API로만 넣을 수 있었으므로 마이그레이션이 `MANUAL`로 표시한다.
- 자동 입력은 출처 `DART`와 [발행조건확정] 접수번호를 남긴다.
  - 권고 사유 끝에 "(DART 수요예측 결과 20260916000234)" 또는 "(수동 입력)"이 붙는다.

### 유상증자 제외
- 판정 순서:
  1. 주요정보
  2. 이미 판정된 딜
  3. 같은 회사의 다른 딜
  4. 공시 본문 핵심어 — 처음 보는 딜만. 원본을 받아야 해서다.
- 판정되면 같은 회사의 판정 전 딜에도 남긴다.
- 유상증자로 판정된 딜은 **지우지 않고** 다음에서만 뺀다(기록 보존):
  - 공모주 목록(`GET /api/ipo`)
  - 권고
  - 청약 알림
- 판정하지 못한 딜(null)은 예전처럼 공모주로 취급한다.

### 스키마 — V11 `ipo_deals` 열 추가
- `offering_kind`: `IPO` | `RIGHTS` | NULL
- `metrics_source`: `DART` | `MANUAL` | NULL
- `metrics_rcept_no`: 자동 입력에 쓴 [발행조건확정] 접수번호

### API와 화면
- `IpoDealView`에 `metricsSource`·`metricsRceptNo`를 추가했다.
- 공모주 화면의 지표 줄 형식: "기관경쟁률 1,187.74:1 · 확약률 21.75% · 자동 입력 — DART [발행조건확정] 수요예측 결과(접수 …)"
- 안내 문구를 자동 입력 기준으로 바꿨다.

## 4. 버린 대안

- **웹 검색(뉴스)으로 입력:** 기사도 같은 공시를 옮긴 것이다. 공시 원본이 더 빠르고 정확하다(기사는 형식이 제각각이고 반올림이 섞인다). 보조로도 쓰지 않는다.
- **공모주 정보 사이트 긁어오기:** 비공식 경로라 형식이 예고 없이 바뀌고, 이용 약관 문제가 있다.
- **건수 기준 확약비율:** 사용자 결정으로 수량 기준을 쓴다. 언론 보도도 수량 기준이다(브릴스 대조).
- **발행공시 목록의 시장 구분으로 유상증자 판정:** 조회 시점 값이라 막 상장한 공모주를 유상증자로 잘못 본다(2절).
- **유상증자 딜 삭제:** 사용자가 남긴 청약 기록이 있을 수 있어, 지우지 않고 숨긴다.
- **엄격한 XML 파서:** 공시 XML에 손으로 만든 표가 섞여 거부될 수 있다. 필요한 것은 표의 글자뿐이라 정규식으로 관대하게 읽는다(`DartDocument`).

## 5. 함정과 주의

- **딜 행:** 딜은 공시(접수번호)마다 한 행이다. 같은 회사의 여러 행에 같은 지표가 들어간다.
  - 같은 회사 여러 행에서 청약 알림이 겹치는 것은 이번 변경 전부터 있던 문제다(후속 과제 — 회사당 최신 행만 알리기).
- **다시 읽지 않음:** 지표가 한 번 채워지면 새 [발행조건확정]이 나와도 다시 읽지 않는다. 틀렸으면 수동 입력으로 고친다.
- **[발행조건확정]이 여러 건일 수 있다:** 최신부터 읽고, 표가 없는 건은 건너뛴다(진코스텍 실측).
- **판정 보류:** 주요정보도 공시 본문도 근거가 없으면 판정을 보류하고 공모주로 둔다(예전 동작). 옛 딜 판정은 다음 배치에 다시 시도한다.
- **응답 크기:** 공시 원본이 WebClient 기본 메모리 한도(256KB)를 넘을 수 있어 DART 클라이언트만 16MB로 올렸다. 압축을 푼 XML은 32MB에서 끊는다.
- **임계값:** 실측 9건 중 현재 임계(500:1, 20%)를 둘 다 넘는 것은 브릴스·멜콘 2건뿐이다. 확약비율이 대체로 낮다(0~36%). 임계 재정의는 D-14(공모주 필터 임계 trial)에서 다룬다.
- **값의 단위:** 확약비율은 0~1로 저장된다. 수동 입력도 0~1이다(화면 안내 그대로).

- **미검증(운영) — 재기동 후 첫 배치(08:20 또는 기동 따라잡기)에서 확인한다:**
  1. 로그에 `공모주 수집 완료 — … 유상증자 제외 N … 옛 딜 공모 종류 판정 N건, 수요예측 지표 자동 입력 N개 회사`가 찍히는지
  2. 로그에 `수요예측 결과 자동 입력: 회사 — 기관경쟁률 …, 의무보유확약비율 …%(수량 기준 …)`가 찍히는지
  3. 공모주 화면에서 유상증자(삼성바이오로직스·뷰노·한울반도체 등)가 사라지는지
  4. 지표 줄에 "자동 입력 — DART …"가 보이는지
